Workshop AWS: e-commerce com Java 21, Spring Boot 4.1 e eventos

Java 21 + Spring Boot 4.1 no ECS Fargate, Lambda Java 21, Step Functions, API Gateway, ALB, IAM, Route 53, ACM, CI/CD e observabilidade com OTel — organizado em 5 módulos para quem está se preparando para uma entrevista técnica.

Objetivo

Ao final, você terá:

  • um domínio público no Route 53 apontando para API Gateway;
  • API Gateway encaminhando tráfego para um ALB interno via VPC Link;
  • um serviço Spring Boot 4.1 rodando em ECS Fargate dentro da VPC;
  • o Spring Web gravando pedidos de e-commerce em RDS PostgreSQL;
  • CDC do PostgreSQL para Kinesis usando AWS DMS;
  • Lambda Java 21 consumindo eventos do Kinesis;
  • Step Functions orquestrando processamento de e-commerce;
  • permissões IAM criadas pelo CDK usando grants;
  • certificados ACM com validação DNS;
  • domínio e certificado ACM no API Gateway;
  • um caminho recomendado de CI/CD;
  • dicas práticas de observabilidade com OpenTelemetry, Honeycomb e Splunk.

Premissa: este workshop assume que você já tem uma hosted zone existente no Route 53, por exemplo example.com. Registrar domínio novo e aguardar delegação DNS é uma etapa separada.

Como estudar este workshop

O conteúdo está organizado em 5 módulos, cada um com três partes: Conceitos antes de começar (o que é, por que existe, como se encaixa na arquitetura), o conteúdo prático (código, CDK, comandos) e Perguntas de entrevista (o que costuma ser perguntado sobre o que você acabou de construir).

Ferramentas, segurança e operação

CloudWatch Logs Serviço de logs centralizados da AWS. Recebe automaticamente os logs de stdout/stderr do ECS e das Lambdas; é a "trilha AWS nativa" citada na seção de observabilidade (Módulo 4).

OIDC OpenID Connect. Protocolo que permite a um provedor externo (GitHub Actions) provar identidade e assumir uma IAM role temporária sem credenciais de longa duração. Usado no pipeline de CI/CD do Módulo 4 para autenticar sem access keys salvas como secret.
DLQ Dead Letter Queue. Destino para onde eventos/mensagens que falharam repetidamente são desviados, em vez de serem perdidos. Sugerido em "Próximos passos" para capturar falhas de Lambda/Step Functions sem perder o pedido.
SnapStart Recurso do Lambda que restaura um ambiente de execução Java a partir de um snapshot pós-inicialização, reduzindo cold start. Coberto em "Próximos passos para produção", como mitigação de cold start citada no Módulo 2.
OpenTelemetry (OTel) / ADOT Padrão aberto de instrumentação para traces, métricas e logs. ADOT é a distribuição da AWS desse padrão (Java Agent, Lambda Layer). Honeycomb / Splunk Backends de observabilidade de terceiros — não são serviços AWS. Honeycomb foca em tracing/debugging de alta cardinalidade; Splunk foca em logs e busca operacional. Fontes de dados diferentes (Módulo 4): Honeycomb recebe traces/métricas via OTLP, através do OTel Collector. Splunk recebe logs via encaminhamento de CloudWatch Logs, não via OTLP.

Fluxo detalhado

  1. Route 53 resolve shop.example.com para o domínio customizado do API Gateway. O nome correto é Route 53, não Route 66.
  2. API Gateway recebe POST /orders, termina TLS com certificado ACM e aplica controles de borda como throttling, auth e WAF, se configurados.
  3. VPC Link conecta rotas do API Gateway a recursos privados na VPC, como ALB interno e aplicações ECS.
  4. ALB interno recebe a chamada vinda do VPC Link e encaminha para o target group do ECS.
  5. ECS Fargate executa o container Spring Boot em subnets privadas. O container não fica exposto diretamente à internet.
  6. Spring Boot Web valida o pedido e grava no PostgreSQL.
  7. RDS PostgreSQL persiste tabelas como orders e order_items.
  8. AWS DMS lê o write-ahead log do PostgreSQL em modo CDC e publica alterações em um Kinesis Data Stream. O target Kinesis do DMS publica registros em JSON.
  9. Lambda consome os registros do Kinesis por event source mapping. A Lambda filtra eventos de e-commerce relevantes, como pedido criado.
  10. Step Functions orquestra o processo: reservar estoque, autorizar pagamento e enviar confirmação.

Módulo 0 — Fundamentos de rede: VPC e Route 53

Por que começar por rede

Todo recurso deste workshop, exceto o Route 53 e a Internet em si, vive dentro de uma VPC: ECS, ALB interno, RDS e DMS. E o único jeito de alguém de fora chegar até essa VPC é através do Route 53 + API Gateway. Se esses dois conceitos não estiverem sólidos, cada módulo seguinte vira "copiar código sem entender por quê". Este módulo é 100% conceitual — não há deploy aqui.

Diagrama — Módulo 0

Route 53 e o Internet Gateway ficam fora da VPC. As três subnets já existem, mas estão vazias — Módulo 1 preenche a Private Subnet com ECS/ALB e a Isolated Subnet com RDS; a ligação de Route 53 até dentro da VPC só aparece no Módulo 4, via API Gateway.

VPC, subnets e roteamento

ConceitoO que éPor que importa aqui
VPC Uma rede virtual isolada dentro da sua conta AWS, com um bloco CIDR próprio (ex.: 10.0.0.0/16). É o "prédio" onde ECS, RDS, DMS e o ALB interno moram. Nada aqui é acessível de fora por padrão.
Subnet pública Subnet com rota para um Internet Gateway. Recursos com IP público conseguem ser alcançados diretamente da internet. Nesta arquitetura, nada de aplicação fica aqui — só o NAT Gateway, se você usar um.
Subnet privada Sem rota direta para a internet, mas com rota de saída via NAT Gateway. Onde o ECS Fargate e o ALB interno rodam — precisam de saída (ex.: puxar imagem do ECR) mas não de entrada pública.
Subnet isolada Sem rota para a internet em nenhuma direção, nem via NAT. Onde RDS e a replication instance do DMS podem rodar — eles não precisam de internet, só de tráfego dentro da VPC.
Internet Gateway (IGW) Componente que permite tráfego entre a VPC e a internet, para subnets públicas. Anexado à VPC, mas o tráfego da aplicação nunca passa direto por ele — só o NAT Gateway usa.
NAT Gateway Permite que recursos em subnet privada iniciem conexões de saída para a internet, sem aceitar conexões de entrada. Deixa o ECS Fargate puxar imagens de container e chamar APIs externas sem expor a task publicamente.
Security Group Firewall stateful por recurso (ENI). Regras de "permitir", avaliadas todas. Controla, por exemplo, quem pode falar com o Spring Boot na porta 8080 (só o ALB) e quem fala com o Postgres na 5432 (só a aplicação e o DMS).
Network ACL Firewall stateless por subnet. Regras de permitir e negar, avaliadas em ordem. Raramente customizada neste tipo de arquitetura — a NACL padrão (permite tudo) é suficiente; security groups fazem o trabalho fino.

Route 53: zonas e registros

ConceitoO que éPor que importa aqui
Hosted zone Um container de registros DNS para um domínio, ex. example.com. É o pré-requisito deste workshop — o CDK faz lookup dessa zone para criar registros novos dentro dela.
Record A Aponta um nome diretamente para um endereço IPv4. Não é o que usamos aqui, porque o IP do API Gateway pode mudar.
Record ALIAS Extensão da AWS ao DNS: aponta um nome para um recurso AWS (API Gateway, ALB, CloudFront) sem IP fixo, resolvido no nível do Route 53. shop.example.com vira um ALIAS para o domínio customizado do API Gateway — funciona até no apex do domínio, o que um CNAME não permite.
Record CNAME Aponta um nome para outro nome (não para um recurso AWS diretamente). Usado pela validação DNS do ACM: o CDK cria um CNAME de validação temporário na hosted zone.
Health check Monitoramento ativo de um endpoint pelo Route 53, usado para failover de DNS. Fora do escopo deste workshop (uma região só), mas é o mecanismo por trás de setups multi-região.

Como isso aparece nesta arquitetura

Olhando o diagrama da seção "Arquitetura": Public Edge tem Route 53 e API Gateway — os únicos pontos alcançáveis da internet. Dentro da VPC, as Private Subnets hospedam o VPC Link, o ALB interno e o ECS Fargate; as Data Subnets hospedam RDS e o DMS. Nenhum desses últimos tem IP público. O tráfego síncrono (pedido do cliente) atravessa Route 53 → API Gateway → VPC Link → ALB → ECS. O tráfego assíncrono (CDC) nunca sai da VPC: Postgres → DMS → Kinesis → Lambda, tudo dentro da rede privada até a Lambda chamar a API do Step Functions (que é um endpoint de serviço AWS, não algo dentro da sua VPC).

Perguntas de entrevista — Módulo 0

  • Subnet pública vs privada vs isolada — qual a diferença real? Pública tem rota para IGW; privada tem rota de saída via NAT mas não de entrada; isolada não tem rota para a internet em nenhuma direção. A diferença é sobre rotas, não sobre "ter IP público" por si só.
  • Para que serve um NAT Gateway, e por que subnets isoladas não precisam de um? NAT Gateway dá saída para a internet a recursos em subnet privada (ex.: ECS puxando imagem do ECR). Subnets isoladas não têm nenhum caminho para a internet — nem de saída — porque os recursos ali (RDS, DMS) só precisam falar com outros recursos dentro da VPC.
  • Por que usar um registro ALIAS em vez de CNAME para o domínio do API Gateway? ALIAS é resolvido no nível do Route 53 (sem round-trip de DNS extra), funciona no apex do domínio (CNAME não pode coexistir com outros registros no apex), e acompanha automaticamente o IP do recurso AWS se ele mudar.
  • Security group vs Network ACL — quando você mexeria em qual? Security group é stateful e por recurso — é o que você ajusta no dia a dia (ex.: liberar porta 8080 do ALB para o ECS). NACL é stateless e por subnet — normalmente só é customizada para bloqueios amplos de rede, não para regras finas de aplicação.
  • Se você tem só uma NAT Gateway para 2 AZs, o que isso custa em disponibilidade? A NAT Gateway é um recurso por AZ; ter uma só cria uma dependência cross-AZ — se a AZ dela cair, toda saída de internet das subnets privadas nas outras AZs para junto. Em produção, o padrão é uma NAT Gateway por AZ.
  • Por que a hosted zone precisa existir antes do deploy, em vez de o CDK criar uma nova? Criar uma hosted zone nova exige delegar os nameservers no registrador do domínio — um passo manual, fora do controle do CDK — e enquanto a delegação não propaga, a validação DNS do ACM (que depende da zone) fica bloqueada. Por isso o workshop assume uma zone já existente e delegada.
  • O que muda se, em vez de subnets isoladas, você colocasse o RDS em subnet privada (com NAT)? Funcionaria, mas o RDS ganharia uma rota de saída para a internet que ele nunca usa — superfície desnecessária. Isolada é mais restritiva e mais correta para um recurso que só precisa de tráfego intra-VPC.

Módulo 1 — ECS e Fargate com Spring Boot

Conceito: ECS, Fargate e "ECS puro"

ECS é o orquestrador de containers. Ele agenda tasks, mantém services rodando, integra com load balancer, health checks, IAM roles, logs e deployment rolling.

Fargate é o modo de compute serverless do ECS. Você não cria nem administra instâncias EC2. Você define imagem, CPU, memória, rede, variáveis e roles; a AWS executa a task.

Quando alguém diz "ECS puro", geralmente quer dizer ECS com EC2 capacity provider: você cria um Auto Scaling Group de instâncias EC2, mantém AMI, patching, escala de hosts, bin packing e capacidade disponível.

CritérioECS FargateECS com EC2
Operação Menor. Sem hosts para manter. Maior. Você mantém EC2, AMI, patching e capacity.
Tempo para começar Melhor para workshop e times que querem foco na aplicação. Exige decisões de instância, ASG e capacity provider.
Custo em escala alta Pode ser mais caro por vCPU/memória. Pode ser mais barato com alta utilização e bom bin packing.
Controle do host Baixo. Sem acesso ao host. Alto. Útil para agentes especiais, GPU, tuning de kernel ou storage local.
Fit para esta arquitetura Bom: API Spring stateless atrás de ALB interno. Excesso inicial, salvo exigência de custo/controle.

Por isso o workshop usa Fargate: a aplicação Spring Boot é stateless, o estado fica no RDS, a entrada é pelo ALB/API Gateway, e o objetivo é reduzir superfície operacional. Migrar para ECS com EC2 depois é possível se custo em escala ou controle de host justificarem.

Conceito: duas roles diferentes por task ECS

Todo task ECS Fargate tem duas IAM roles com propósitos diferentes — uma confusão clássica de entrevista:

RoleQuem assumePara quê
Task execution role O agente do ECS, antes da sua aplicação rodar. Puxar a imagem do ECR, buscar secrets/parameters referenciados na task definition, escrever logs no CloudWatch.
Task role Sua aplicação, em tempo de execução (via credenciais injetadas no container). Permissões de negócio: chamar outros serviços AWS que o código Java realmente invoca (neste workshop, nenhuma chamada direta é feita do Spring Boot a outro serviço AWS — o acesso ao Postgres é por rede/credenciais, não IAM).

Diagrama — Módulo 1

A Private Subnet do Módulo 0 ganha o ALB interno e a task ECS; a Isolated Subnet ganha o RDS. As security groups (AlbSg → AppSg na porta 8080, AppSg → DbSg na porta 5432) são o que efetivamente restringe quem fala com quem — não a topologia de subnet por si só.

Perguntas de entrevista — Módulo 1

  • Fargate vs launch type EC2 — quando escolher cada um? Fargate quando você quer não gerenciar hosts e a carga é razoavelmente previsível; EC2 quando precisa de controle de host (GPU, kernel tuning, storage local) ou quer otimizar custo via bin packing em alta utilização.
  • Qual a diferença entre task execution role e task role? A execution role é usada pelo próprio ECS antes do seu código rodar (pull de imagem, secrets, logs). A task role é usada pelo seu código em runtime para chamar outros serviços AWS.
  • Como o ECS sabe que uma task está saudável? Via health check do target group do ALB (HTTP, ex. GET /health) e, opcionalmente, um container health check próprio na task definition; falhas consecutivas fazem o ECS substituir a task.
  • Por que expor só health/info no Actuator, em vez de também /actuator/prometheus? Porque este workshop não faz scrape de Prometheus — quem exporta métricas é o OpenTelemetry Java Agent, via OTLP até o Honeycomb (Módulo 4). Adicionar Micrometer/Prometheus só faria sentido se algo realmente fizesse scrape desse endpoint (ex.: um Prometheus self-managed ou o Managed Service for Prometheus da AWS); sem um consumidor, é uma dependência e um endpoint sem uso real.
  • Como você faria rolling deploy de uma nova versão sem downtime? ECS já faz rolling update por padrão (sobe tasks novas, espera health check passar, só então derruba as antigas); para mais segurança, ative o deployment circuit breaker (reverte automaticamente se as tasks novas falharem health check) e mantenha minHealthyPercent/maxHealthyPercent adequados.
  • O que acontece se você definir cpu/memoryLimitMiB baixo demais na task? A JVM pode sofrer OOM kill (o container é morto pelo cgroup, não uma exceção Java tratável) ou throttling de CPU, aumentando latência sem erro explícito — por isso monitorar utilização real antes de reduzir agressivamente.
  • Por que desiredCount(2) em vez de 1? Redundância entre AZs: com 2 tasks, o ECS tenta distribuí-las em AZs diferentes, então a perda de uma AZ não tira o serviço do ar — com 1 task você tem um SPOF de compute.

Módulo 2 — Lambda e Step Functions

Conceito: modelo de execução da Lambda e cold starts em Java

Uma Lambda não fica sempre rodando: a AWS cria um ambiente de execução sob demanda, roda seu handler, e pode reutilizar esse ambiente para invocações seguintes (warm start) ou descartá-lo. A primeira invocação em um ambiente novo é um cold start: inicialização da JVM, carregamento de classes, inicialização do seu código estático (ex.: criar o SfnClient).

Java sofre mais com cold start do que runtimes interpretados como Node/Python, porque a JVM tem mais trabalho de inicialização. As mitigações mais comuns: provisioned concurrency (mantém ambientes já quentes) e SnapStart (restaura de um snapshot pós-inicialização — ver Módulo 4, "Próximos passos").

Conceito: Step Functions — Standard vs Express, orquestração vs coreografia

CritérioStandard WorkflowExpress Workflow
Duração máxima Até 1 ano Até 5 minutos
Semântica de execução Exactly-once At-least-once
Histórico de execução Visível e auditável no console por execução Só via CloudWatch Logs, não por execução individual
Custo/volume Por transição de estado — melhor para workflows de negócio de baixo/médio volume Por invocação e duração — melhor para altíssimo volume de eventos curtos
Fit para este workshop Sim — poucos pedidos por segundo, precisa de auditoria (reserva de estoque, pagamento), exactly-once importa para não cobrar duas vezes. Melhor para pipelines de streaming de altíssima frequência sem necessidade de auditoria por execução.

A outra distinção importante: orquestração (um componente central, aqui o Step Functions, decide e chama cada passo) vs. coreografia (cada serviço reage a eventos e decide sozinho o que fazer, tipicamente via SNS/SQS/EventBridge). Este workshop usa orquestração para o workflow de negócio — você quer um lugar único para ver o estado de um pedido — mas usa um estilo mais próximo de coreografia no lado do CDC (o Postgres não sabe que o DMS existe; o DMS não sabe quem consome o Kinesis).

Conceito: Amazon States Language (ASL)

Por baixo de qualquer state machine do Step Functions — inclusive as que você define em CDK — existe um documento JSON na Amazon States Language. O CDK não é uma linguagem paralela: Chain, LambdaInvoke, addRetry e addCatch são só uma forma de programar em Java o que vira, no cdk synth, um bloco ASL como este:

  "States": {
    "ReserveInventoryStep": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Next": "AuthorizePaymentStep"

Os tipos de estado que mais aparecem em entrevista: Task (executa um trabalho, ex. invocar uma Lambda), Choice (ramifica com base em uma condição no input), Parallel (executa ramos simultâneos), Map (aplica os mesmos passos a uma lista de itens) e Wait (pausa por tempo fixo ou até um timestamp). Este workshop usa só Task, Retry/Catch e Fail — o suficiente para o workflow de pedido, mas vale saber que Choice/Parallel/Map existem para workflows mais ramificados.

workflow-lambda/src/main/java/com/example/OrderEventRouterHandler.java

Esta é a Lambda que consome o Kinesis (alimentado pelo DMS — ver Módulo 3) e inicia uma execução da Step Function para cada pedido criado.

package com.example;

import com.amazonaws.services.lambda.runtime.Context;
import com.amazonaws.services.lambda.runtime.RequestHandler;
import com.amazonaws.services.lambda.runtime.events.KinesisEvent;
import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import software.amazon.awssdk.services.sfn.SfnClient;
import software.amazon.awssdk.services.sfn.model.StartExecutionRequest;

import java.nio.charset.StandardCharsets;

public class OrderEventRouterHandler implements RequestHandler<KinesisEvent, Void> {
    private final ObjectMapper mapper = new ObjectMapper();
    private final SfnClient sfn = SfnClient.create();

    @Override
    public Void handleRequest(KinesisEvent event, Context context) {
        for (KinesisEvent.KinesisEventRecord record : event.getRecords()) {
            try {
                String json = StandardCharsets.UTF_8.decode(record.getKinesis().getData()).toString();
                JsonNode root = mapper.readTree(json);

                String table = root.path("metadata").path("table-name").asText();
                String operation = root.path("metadata").path("operation").asText();

                if (!"orders".equals(table) || !"insert".equals(operation)) {
                    continue;
                }

                JsonNode data = root.path("data");
                sfn.startExecution(StartExecutionRequest.builder()
                        .stateMachineArn(System.getenv("STATE_MACHINE_ARN"))
                        .name("order-" + data.path("id").asText())
                        .input(data.toString())
                        .build());
            } catch (Exception e) {
                throw new RuntimeException("Failed to route Kinesis CDC record", e);
            }
        }
        return null;
    }
}

Definindo o state machine no CDK

Este é o pedaço que faltava em versões anteriores deste material: o objeto stateMachine referenciado mais adiante (Módulo 3, para dar permissão à Lambda roteadora de iniciar execuções) precisa ser definido em algum lugar. Ele é definido aqui, porque conceitualmente é aqui que o workflow de Step Functions nasce.

import software.amazon.awscdk.services.lambda.Function;
import software.amazon.awscdk.services.lambda.Runtime;
import software.amazon.awscdk.services.lambda.Code;
import software.amazon.awscdk.services.stepfunctions.StateMachine;
import software.amazon.awscdk.services.stepfunctions.StateMachineType;
import software.amazon.awscdk.services.stepfunctions.DefinitionBody;
import software.amazon.awscdk.services.stepfunctions.Fail;
import software.amazon.awscdk.services.stepfunctions.IChainable;
import software.amazon.awscdk.services.stepfunctions.RetryProps;
import software.amazon.awscdk.services.stepfunctions.CatchProps;
import software.amazon.awscdk.services.stepfunctions.tasks.LambdaInvoke;

import java.util.List;

// Um Lambda por passo do workflow, cada um com sua própria classe de handler
// no mesmo jar — o nome da função e o handler já dizem o que ela faz.
Function reserveInventory = Function.Builder.create(this, "ReserveInventoryFunction")
        .runtime(Runtime.JAVA_21)
        .handler("com.example.ReserveInventoryHandler::handleRequest")
        .code(Code.fromAsset("../workflow-lambda/target/workflow-lambda.jar"))
        .build();

Function authorizePayment = Function.Builder.create(this, "AuthorizePaymentFunction")
        .runtime(Runtime.JAVA_21)
        .handler("com.example.AuthorizePaymentHandler::handleRequest")
        .code(Code.fromAsset("../workflow-lambda/target/workflow-lambda.jar"))
        .build();

Function sendConfirmation = Function.Builder.create(this, "SendConfirmationFunction")
        .runtime(Runtime.JAVA_21)
        .handler("com.example.SendConfirmationHandler::handleRequest")
        .code(Code.fromAsset("../workflow-lambda/target/workflow-lambda.jar"))
        .build();

LambdaInvoke reserveStep = LambdaInvoke.Builder.create(this, "ReserveInventoryStep")
        .lambdaFunction(reserveInventory)
        .outputPath("$.Payload")
        .build();

LambdaInvoke paymentStep = LambdaInvoke.Builder.create(this, "AuthorizePaymentStep")
        .lambdaFunction(authorizePayment)
        .outputPath("$.Payload")
        .build();

LambdaInvoke confirmationStep = LambdaInvoke.Builder.create(this, "SendConfirmationStep")
        .lambdaFunction(sendConfirmation)
        .outputPath("$.Payload")
        .build();

Fail orderFailed = Fail.Builder.create(this, "OrderFailed")
        .cause("Order could not be fulfilled")
        .build();

// Se a autorização de pagamento falhar, o workflow vai para o estado de falha
// em vez de tentar confirmar um pedido que não foi pago.
paymentStep.addCatch(orderFailed, CatchProps.builder()
        .errors(List.of("States.ALL"))
        .build());

// Falhas transitórias (ex.: throttling do provedor de pagamento) tentam de novo
// antes de desistir.
paymentStep.addRetry(RetryProps.builder()
        .errors(List.of("States.TaskFailed"))
        .maxAttempts(2)
        .backoffRate(2.0)
        .build());

IChainable definition = reserveStep.next(paymentStep).next(confirmationStep);

StateMachine stateMachine = StateMachine.Builder.create(this, "EcommerceWorkflow")
        .definitionBody(DefinitionBody.fromChainable(definition))
        .stateMachineType(StateMachineType.STANDARD)
        .build();

O CDK cuida de criar a role de execução do state machine com permissão lambda:InvokeFunction nas três Lambdas automaticamente, porque LambdaInvoke chama grantInvoke internamente ao ser adicionado à definição.

Testando um estado isoladamente com a TestState API

Antes de rodar a state machine inteira, dá para testar a definição ASL de um único estado — sem publicar nem atualizar o state machine — com a TestState API do Step Functions (aws stepfunctions test-state na CLI). Para um estado Task como os deste workshop, ela de fato invoca a Lambda de verdade; o que ela evita é ter que dar deploy na state machine inteira só para descobrir se o ResultSelector ou o Parameters de um passo estão certos.

aws stepfunctions test-state \
  --definition '{
    "Type": "Task",
    "Resource": "arn:aws:states:::lambda:invoke",
    "Parameters": {
      "FunctionName": "arn:aws:lambda:us-east-1:123456789012:function:AuthorizePaymentFunction",
      "Payload.$": "$"
    },
    "ResultSelector": {
      "authorized.$": "$.Payload.authorized"
    }
  }' \
  --input '{"orderId": "abc-123", "amount": 39.90}' \
  --role-arn arn:aws:iam::123456789012:role/EcommerceWorkflowRole \
  --inspection-level TRACE

--inspection-level controla o quanto de detalhe volta na resposta: INFO só o resultado final; DEBUG acrescenta input/output brutos; TRACE mostra cada estágio do processamento de dados (após InputPath, após Parameters, resultado bruto da Lambda, após ResultSelector, após OutputPath) — o nível mais útil quando um campo não chega onde deveria e você não sabe em qual dessas etapas ele se perdeu.

A role em --role-arn precisa de states:TestState e, para um Task Lambda, também lambda:InvokeFunction na função-alvo. E vale repetir: isso testa um estado com uma invocação real — não é um mock. Para verificar o workflow completo já publicado, ponta a ponta, o Módulo 4 usa aws stepfunctions describe-execution; os dois se complementam, um para depurar durante o desenvolvimento, o outro para validar a execução real em produção.

Perguntas de entrevista — Módulo 2

  • Por que Lambda aqui em vez de um consumidor de longa duração? O volume de eventos de CDC por pedido é baixo e o processamento é curto; Lambda com event source mapping escala automaticamente com o stream sem você gerenciar um processo sempre ligado.
  • Standard ou Express Step Functions — qual e por quê? Standard, porque cada execução representa um pedido de negócio que precisa ser auditável individualmente e a semântica é exactly-once — importante para não autorizar pagamento duas vezes.
  • Como você evita perder um pedido se um passo falhar? addRetry cobre falhas transitórias com backoff; addCatch direciona falhas persistentes para um estado de compensação/falha explícito (aqui, Fail) em vez de deixar a execução travada ou silenciosamente incompleta.
  • Por que usar três handlers separados em vez de um handler genérico com variável de ambiente? Clareza operacional: cada função aparece no console, nos logs e na definição ASL já identificada pelo que faz, sem precisar abrir a configuração para ver qual ECOMMERCE_STEP está setado. O custo é mais classes repetidas — um trade-off razoável para três passos fixos, mas que não escalaria bem para dezenas de passos.
  • Como você testaria a lógica de um único passo do workflow sem rodar a state machine inteira? Com a TestState API (aws stepfunctions test-state): passa a definição ASL de um estado e um input, e recebe o resultado real daquele estado isolado, incluindo, com --inspection-level TRACE, cada estágio de processamento de dados (InputPath, Parameters, resultado, ResultSelector, OutputPath).
  • Como você reduziria o cold start desta Lambda em Java sem mudar de linguagem? Provisioned concurrency (mantém ambientes quentes, com custo constante) ou SnapStart (restaura de snapshot pós-init, só em versões publicadas — ver "Próximos passos"); também ajuda reduzir dependências no shaded jar e evitar inicialização pesada em código estático.
  • O que muda no ASL se você quisesse rodar os três passos em paralelo em vez de em sequência? Trocar a cadeia reserveStep.next(paymentStep).next(confirmationStep) por um estado Parallel com um ramo por Lambda — mas aqui a sequência importa (não faz sentido confirmar antes de autorizar pagamento), então paralelo não se aplica a este workflow específico.
  • Quantas execuções concorrentes o Step Functions Standard aguenta, e o que acontece se estourar? Existe uma cota de execuções em StartExecution por conta/região (soft limit, pode pedir aumento); ao estourar, novas chamadas de StartExecution falham com throttling — a Lambda roteadora precisaria de retry com backoff nesse caso.

Módulo 3 — CDC (DMS/Kinesis) e infraestrutura completa em CDK

Conceito: por que CDC em vez de publicar eventos direto do app

  • O commit do pedido e a publicação do evento não ficam em duas transações separadas no app (evita o problema clássico de "salvei no banco mas falhei ao publicar o evento", conhecido como dual-write).
  • Se a Lambda ou Step Functions ficarem fora do ar por alguns minutos, os dados continuam no banco e o stream pode recuperar assim que voltarem.
  • O Spring Web continua simples: recebe HTTP, valida e grava no Postgres. Nenhuma lógica de publicação de evento no código da aplicação.

A alternativa mais comum a CDC é o padrão outbox (o app grava o evento em uma tabela outbox na mesma transação, e um processo separado publica a partir dela). CDC via DMS evita até essa tabela extra, lendo diretamente do write-ahead log do Postgres — o trade-off é depender da configuração de replication lógica do banco e de um componente AWS a mais (DMS) no caminho.

Conceito: o que o DMS realmente faz

DMS (Database Migration Service) não é só para migrações pontuais — em modo CDC contínuo, ele se conecta como um "replica" lógico do Postgres, lê o stream de mudanças do write-ahead log, e publica cada mudança (insert/update/delete) no destino configurado — aqui, um Kinesis Data Stream, em JSON.

Conceito: Kinesis como buffer durável

Entre o DMS e a Lambda, o Kinesis existe para desacoplar produtor e consumidor: se a Lambda estiver lenta ou fora do ar, os registros continuam retidos no stream (por padrão, 24h) até serem consumidos, em vez de serem perdidos ou de bloquear o DMS.

Conceito: CDK L1 (Cfn*) vs L2 constructs

O CDK tem "níveis" de abstração, e este módulo usa os dois de propósito:

  • L1 (Cfn*) — mapeamento quase 1:1 com um recurso CloudFormation, sem opinião nenhuma. É o que existe para todo recurso AWS, mesmo os mais novos ou de nicho. Usado abaixo para DMS (CfnReplicationInstance, CfnEndpoint, CfnReplicationTask) porque o CDK ainda não tem um construct L2 maduro para DMS.
  • L2 — uma classe com opinião, que já embute boas práticas e expõe métodos convenientes. É o que este workshop usa para ECS (ApplicationLoadBalancedFargateService já cria ALB, target group e task definition) e para permissões (orderChanges.grantRead(eventRouter)).

O que um .grantRead()/.grantWrite() realmente faz: gera uma iam:PolicyStatement concreta (com as actions certas, ex. kinesis:GetRecords) e anexa à role do recurso que recebe a permissão. Não é mágica nem uma abstração nova de segurança — é geração de IAM policy, só que você não escreve o JSON à mão. Isso é útil de saber em entrevista: se perguntarem "o que o CDK gera por trás de um grant", a resposta é "uma policy IAM normal, anexada à role certa".

DMS no CDK: código real

Diferente de uma descrição em comentários, este é o esqueleto real dos L1 constructs de DMS: subnet group, replication instance, os dois endpoints (source e target) e a replication task.

import software.amazon.awscdk.services.dms.CfnReplicationSubnetGroup;
import software.amazon.awscdk.services.dms.CfnReplicationInstance;
import software.amazon.awscdk.services.dms.CfnEndpoint;
import software.amazon.awscdk.services.dms.CfnReplicationTask;
import software.amazon.awscdk.services.iam.Role;
import software.amazon.awscdk.services.iam.ServicePrincipal;
import software.amazon.awscdk.services.ec2.ISubnet;

import java.util.stream.Collectors;

// Role assumida pelo DMS para poder escrever no Kinesis target.
Role dmsRole = Role.Builder.create(this, "DmsKinesisRole")
        .assumedBy(new ServicePrincipal("dms.amazonaws.com"))
        .build();
orderChanges.grantWrite(dmsRole);

SecurityGroup dmsSg = SecurityGroup.Builder.create(this, "DmsSg")
        .vpc(vpc)
        .allowAllOutbound(true)
        .build();
dbSg.addIngressRule(dmsSg, Port.tcp(5432), "DMS lê o Postgres via CDC");

CfnReplicationSubnetGroup subnetGroup = CfnReplicationSubnetGroup.Builder.create(this, "DmsSubnetGroup")
        .replicationSubnetGroupDescription("Subnets para a replication instance do DMS")
        .subnetIds(vpc.getIsolatedSubnets().stream()
                .map(ISubnet::getSubnetId)
                .collect(Collectors.toList()))
        .build();

CfnReplicationInstance replicationInstance = CfnReplicationInstance.Builder.create(this, "DmsReplicationInstance")
        .replicationInstanceClass("dms.t3.micro")
        .replicationSubnetGroupIdentifier(subnetGroup.getRef())
        .vpcSecurityGroupIds(List.of(dmsSg.getSecurityGroupId()))
        .publiclyAccessible(false)
        .build();

CfnEndpoint sourceEndpoint = CfnEndpoint.Builder.create(this, "PostgresSourceEndpoint")
        .endpointType("source")
        .engineName("postgres")
        .serverName(db.getDbInstanceEndpointAddress())
        .port(5432)
        .databaseName("ecommerce")
        .username("postgres")
        .password(db.getSecret().secretValueFromJson("password").unsafeUnwrap())
        .build();

CfnEndpoint targetEndpoint = CfnEndpoint.Builder.create(this, "KinesisTargetEndpoint")
        .endpointType("target")
        .engineName("kinesis")
        .kinesisSettings(CfnEndpoint.KinesisSettingsProperty.builder()
                .streamArn(orderChanges.getStreamArn())
                .serviceAccessRoleArn(dmsRole.getRoleArn())
                .build())
        .build();

CfnReplicationTask replicationTask = CfnReplicationTask.Builder.create(this, "OrdersCdcTask")
        .replicationInstanceArn(replicationInstance.getRef())
        .sourceEndpointArn(sourceEndpoint.getRef())
        .targetEndpointArn(targetEndpoint.getRef())
        .migrationType("cdc")
        .tableMappings("{\"rules\":[{\"rule-type\":\"selection\",\"rule-id\":\"1\","
                + "\"rule-name\":\"include-orders\",\"object-locator\":{\"schema-name\":\"public\","
                + "\"table-name\":\"orders\"},\"rule-action\":\"include\"}]}")
        .build();

unsafeUnwrap() materializa o segredo em texto durante o synth do CDK — aceitável para um workshop de laboratório, mas evite em qualquer stack que vá para um repositório compartilhado ou pipeline real; prefira resolver a senha em runtime via Secrets Manager sempre que o serviço de destino suportar (DMS endpoints, no momento em que este material foi escrito, aceitam autenticação via Secrets Manager como alternativa).

Como essa parte é a mais sensível e a que mais demora para provisionar (a replication instance sozinha pode levar vários minutos para ficar disponível), vale validar primeiro manualmente no console do DMS em um ambiente de laboratório antes de confiar cegamente no CDK synth.

Perguntas de entrevista — Módulo 3

  • Por que CDC em vez de publicar o evento direto do código da aplicação? Evita dual-write (banco e evento em transações separadas que podem divergir), mantém o Spring Web simples, e sobrevive a indisponibilidade temporária dos consumidores porque o dado já está durável no banco.
  • O que a replicação lógica do Postgres exige? O parâmetro rds.logical_replication = 1 no parameter group (com reboot), e opcionalmente REPLICA IDENTITY FULL por tabela se você precisar do before-image completo em updates/deletes.
  • Por que colocar um ALB interno atrás do API Gateway em vez de expor o ALB direto? Mantém um único ponto de entrada público controlado (API Gateway: TLS, throttling, auth, WAF), enquanto o ALB e o ECS ficam inatingíveis de fora da VPC — reduz superfície de ataque.
  • O que muda entre Standard e Serverless para a replication instance do DMS? Standard exige provisionar e dimensionar uma instância (dms.t3.micro etc.) que você paga mesmo ociosa; Serverless escala automaticamente com a carga de CDC, à custa de menos controle fino sobre a capacidade.
  • Por que a seção de DMS usa L1 constructs (CfnReplicationInstance) em vez de uma classe de alto nível como a do ECS? Porque o CDK ainda não tem um construct L2 maduro para DMS — L1 é o "piso": mapeia quase 1:1 com o recurso CloudFormation, existe para praticamente tudo, mas exige que você monte manualmente o que um L2 faria por você (subnet group, roles, etc.).
  • O que exatamente um .grantWrite(dmsRole) faz por baixo dos panos? Gera uma iam:PolicyStatement com as actions necessárias (ex.: kinesis:PutRecord, kinesis:PutRecords) escopada ao ARN daquele stream específico, e anexa essa policy à role passada como argumento — não é uma abstração de segurança nova, é geração de IAM policy.
  • Se o DMS parar de conseguir escrever no Kinesis, onde você olharia primeiro? Métricas da replication task no console do DMS (erros, latência de CDC), depois a IAM role do DMS (a policy gerada pelo grantWrite ainda está correta? o stream ainda existe com o mesmo ARN?), e por fim se o Kinesis está sendo throttled por excesso de writes.
  • Por que rodar o ECS em desiredCount(2) mas a replication instance do DMS como uma instância só? DMS CDC contínuo não tem um modelo nativo de multi-instância ativa-ativa como o ECS; alta disponibilidade em DMS normalmente vem de uma instância multi-AZ (standby), não de várias instâncias processando o mesmo CDC em paralelo — replicar o mesmo CDC duas vezes duplicaria eventos.

Módulo 4 — DNS/ACM, deploy, CI/CD e observabilidade

Conceito: validação ACM e a regra da região

Um certificado ACM só é utilizável pelo serviço AWS que está na mesma região do certificado — com uma exceção conhecida: CloudFront e API Gateway edge-optimized exigem o certificado em us-east-1, não importa em qual região o resto do stack vive. Como este workshop usa API Gateway regional, o certificado fica na mesma região do stack.

A validação em si é feita criando um registro CNAME temporário na hosted zone (Módulo 0) provando que você controla o domínio. Se a hosted zone já é gerenciada pelo próprio CDK/conta, a validação é automática porque o CDK cria esse CNAME sozinho.

Conceito: por que OIDC em vez de access keys no CI

Uma access key IAM tradicional é uma credencial de longa duração armazenada como secret do CI — se vazar, é válida até ser revogada manualmente. OIDC (OpenID Connect) permite que o GitHub Actions assuma uma role temporária na AWS sem nenhum secret armazenado: a AWS confia em tokens assinados pelo GitHub para aquele repositório/branch específico, e a credencial resultante expira em minutos.

Na prática, isso é uma trust policy na role IAM, com uma condição sobre a claim sub do token OIDC — algo como:

{
  "Effect": "Allow",
  "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
    "StringLike": { "token.actions.githubusercontent.com:sub": "repo:minha-org/meu-repo:ref:refs/heads/main" }
  }
}

É essa condição em sub que impede que um workflow de outro repositório, ou até de uma branch diferente do mesmo repositório, consiga assumir a mesma role — sem isso, qualquer repositório que confiasse no mesmo provedor OIDC da conta poderia pedir a credencial.

Conceito: o papel do OpenTelemetry

OpenTelemetry (OTel) é uma camada de instrumentação neutra de fornecedor para traces, métricas e logs. A ideia é instrumentar uma vez (Java Agent no ECS, ADOT no Lambda) e depois escolher/trocar backends (Honeycomb, Splunk, CloudWatch) sem reinstrumentar o código.

Diagrama — Módulo 4a: DNS/ACM e CI/CD

Os dois fluxos são independentes: o da esquerda entrega o domínio público (Módulo 0 + ACM); o da direita é como as mudanças chegam à conta AWS sem access keys de longa duração.

Route 53 e certificados ACM

Agora domínio e certificado fazem parte do caminho principal. O CDK faz quatro coisas:

Consultando a execução da Step Function

A Lambda roteadora (Módulo 2) nomeia cada execução como order-<orderId> (.name("order-" + data.path("id").asText())), então o ARN da execução é previsível a partir do orderId retornado pelo POST /orders. Ainda assim, os três jeitos de consultar o estado servem para perguntas diferentes:

aws stepfunctions list-executions \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:EcommerceWorkflow \
  --status-filter FAILED \
  --max-results 5

list-executions responde "quais execuções existem e com que status" — útil quando você não sabe o orderId de antemão, ou quer só as que falharam (--status-filter FAILED), sem abrir uma por uma.

aws stepfunctions describe-execution \
  --execution-arn arn:aws:states:us-east-1:123456789012:execution:EcommerceWorkflow:order-abc-123

describe-execution responde "essa execução específica terminou, e como" — status geral (RUNNING/SUCCEEDED/FAILED/TIMED_OUT/ABORTED) mais o input/output completo da execução. Não diz em qual state ela parou.

aws stepfunctions get-execution-history \
  --execution-arn arn:aws:states:us-east-1:123456789012:execution:EcommerceWorkflow:order-abc-123 \
  --reverse-order

get-execution-history responde "onde exatamente ela está ou travou" — o histórico completo de eventos (StateEntered, TaskSucceeded, TaskFailed, StateExited, etc.), cada um com timestamp e o input/output daquele momento. Não existe um campo único "estado atual" na API do Step Functions: com --reverse-order o histórico já vem do mais recente para o mais antigo, então o estado atual é, na prática, o primeiro evento StateEntered da lista que ainda não tem um StateExited correspondente.

Observabilidade com OTel, Honeycomb e Splunk

Se o time já usa OpenTelemetry, Honeycomb e Splunk, trate OTel como trilha principal. Antes de configurar qualquer coisa, é importante deixar explícito de onde vem o dado de cada backend — não é o mesmo caminho para os dois:

Honeycomb recebe traces e métricas, enviados via OTLP diretamente pela instrumentação (Java Agent no ECS, ADOT no Lambda), passando pelo OTel Collector, em tempo quase real.

Splunk recebe logs, mas não pelo mesmo caminho OTLP: os logs saem via stdout/stderr para o driver de log nativo do ECS/Lambda, viram CloudWatch Logs, e só então são encaminhados de lá para o Splunk. É por isso que, na configuração do Java Agent mais abaixo, OTEL_LOGS_EXPORTER fica como none — o workshop propositalmente não duplica logs pelo caminho OTLP.

Diagrama — Módulo 4b: observabilidade

Linha sólida = caminho OTLP (traces/métricas → Honeycomb). Linha tracejada = caminho de log (stdout/stderr → CloudWatch → Splunk). São duas fontes de dados diferentes, não a mesma informação duplicada em dois lugares — por isso OTEL_LOGS_EXPORTER=none.

Aside: se o backend for a Splunk Observability Cloud (não o Splunk clássico de busca de logs) e o time quiser traces/métricas lá também, dá para apontar o OTel Collector para ela via um exportador próprio, em paralelo ao exportador do Honeycomb. Isso é um terceiro caminho opcional e independente — não o mesmo fluxo de "Logs para Splunk" descrito acima.

Spring Boot 4.1 no ECS com Java Agent

O caminho mais rápido é usar o OpenTelemetry Java Agent. Baixe o agent no build da imagem ou copie de um estágio separado.

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY opentelemetry-javaagent.jar /otel/opentelemetry-javaagent.jar
COPY target/spring-api-0.0.1.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-javaagent:/otel/opentelemetry-javaagent.jar", "-jar", "app.jar"]

Configure por variáveis de ambiente no ECS task definition:

OTEL_SERVICE_NAME=spring-api
OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod,service.version=1.0.0
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector.local:4317
OTEL_TRACES_EXPORTER=otlp
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=none

OTEL_LOGS_EXPORTER=none é proposital, não um esquecimento: traces e métricas vão para o Collector via OTLP e chegam ao Honeycomb; logs seguem o caminho separado (stdout/stderr → CloudWatch → Splunk) explicado acima, então não faz sentido também exportá-los via OTLP — seria a mesma informação duplicada em dois lugares.

Para um primeiro teste sem Collector, você pode exportar traces/métricas direto para Honeycomb usando OTLP HTTP:

OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf

Perguntas de entrevista — Módulo 4

  • Por que OIDC em vez de access keys de longa duração no CI? OIDC troca um secret estático (que pode vazar e continuar válido) por uma credencial temporária emitida por confiança em tokens assinados do provedor de CI, escopada a repositório/branch e expirando em minutos.
  • Qual a diferença real entre trace, log e métrica no OTel? Trace é a linha do tempo estruturada de uma requisição através de serviços (spans com relação pai/filho); log é um evento pontual com texto/contexto; métrica é um valor numérico agregado ao longo do tempo (contador, gauge, histograma). Os três compartilham contexto (ex.: trace_id) para correlação.
  • Um request teve sucesso no Spring Boot mas nunca chegou ao Step Functions — como você debugaria? Seguindo a cadeia assíncrona: confirmar o insert no RDS, checar métricas/logs da replication task do DMS (ela processou o commit?), verificar se o registro chegou ao Kinesis (iterator age, incoming records), checar invocações/erros da Lambda roteadora, e por fim procurar (ou a ausência de) uma execução no Step Functions com o nome esperado.
  • Step Functions é stateful — então como você consulta esse estado via API? Três chamadas para três perguntas diferentes: ListExecutions ("quais execuções existem e com que status"), DescribeExecution ("essa execução específica terminou, e como"), e GetExecutionHistory ("em qual state exatamente ela está ou travou" — via o evento StateEntered mais recente sem StateExited correspondente). Não existe uma chamada única que devolva só "o estado atual" — é o histórico completo, e você infere a partir dele.
  • Por que o certificado ACM precisa estar em us-east-1 às vezes, mas não sempre? Só quando o certificado é usado por um serviço "edge" global — CloudFront ou API Gateway edge-optimized. API Gateway regional (usado neste workshop) aceita o certificado na mesma região do stack.
  • Na trust policy do OIDC, o que impede um workflow de outro repositório de assumir a mesma role? A condição StringLike sobre a claim sub do token (ex.: repo:org/repo:ref:refs/heads/main) — sem essa condição, qualquer repositório que confiasse no mesmo provedor OIDC da conta poderia pedir a credencial.
  • Por que não exportar logs via OTLP também, já que traces e métricas já vão por ali? Porque este workshop já tem um caminho de logs via CloudWatch → Splunk; exportar logs também via OTLP duplicaria a mesma informação em dois lugares e complicaria correlação — a escolha aqui é ter uma única fonte por tipo de dado.
  • Como você garantiria zero downtime durante um cdk deploy em produção? ECS já faz rolling update com health check no target group; o ponto de atenção real é a migration do Flyway (Módulo 1) ser compatível com a versão anterior do app ainda rodando durante o rolling update (ex.: não remover uma coluna que a versão antiga ainda lê), e, para o CDK em si, revisar o cdk diff antes de aplicar para pegar replacements destrutivos (ex.: troca de RDS que force recriação).
  • Quem tem permissão para aprovar o cdk deploy em produção neste pipeline? Na configuração mínima do workshop, ninguém além do próprio workflow — é exatamente por isso que "Dicas práticas de CI/CD" recomenda aprovação manual (environment protection rules do GitHub) antes do deploy em prod, não só depender da role IAM estar certa.

Legenda: ⓪ Módulo 0 — rede (VPC, Route 53) · ① Módulo 1 — ECS/Fargate, ALB, RDS · ② Módulo 2 — Lambda e Step Functions · ③ Módulo 3 — CDC (DMS/Kinesis) e a fiação completa em CDK · ④ Módulo 4 — DNS/ACM, CI/CD e observabilidade.

Perguntas de entrevista — visão geral do sistema

  • Descreva o ciclo de vida completo de um pedido, do POST /orders até a confirmação. Route 53 → API Gateway (TLS/ACM) → VPC Link → ALB interno → ECS Fargate → grava no RDS → DMS captura o insert via CDC → publica no Kinesis → Lambda roteadora inicia a Step Function → reserva de estoque → autorização de pagamento (com retry/catch) → confirmação.
  • Onde estão os pontos únicos de falha nesta arquitetura? O RDS é a maior candidata (sem Multi-AZ, é um SPOF de dados); a replication instance do DMS também, se não houver failover configurado; o Kinesis e o ECS já são multi-AZ por padrão com desiredCount(2).
  • Como você reduziria custo sem sacrificar a arquitetura? Substituir o NAT Gateway (cobrado por hora + por GB) por VPC Endpoints para ECR/S3 se o único uso da saída for pull de imagem; avaliar DMS Serverless em vez de uma replication instance sempre ligada; usar Fargate Spot para tasks não críticas.
  • Como você adicionaria uma segunda região? RDS via read replica cross-region ou Aurora Global Database; Route 53 com routing policy de failover/latência e health checks; replicar o stack CDK por região, com o DMS/Kinesis por região (CDC não cruza região sozinho).
  • Um registro "poison pill" trava o consumo do Kinesis pela Lambda — o que fazer? Configurar bisectBatchOnFunctionError e um número máximo de tentativas no event source mapping, com um destino on-failure (ex.: outro stream ou SQS) para isolar o registro problemático e não bloquear o shard inteiro.
  • O tráfego aumenta 100x da noite para o dia — o que quebra primeiro? Provavelmente o RDS (conexões/IOPS) e a replication instance do DMS antes do ECS (que escala tasks) ou do Kinesis (que escala por shards); o Step Functions Standard também tem limite de execuções concorrentes por conta a considerar.
  • Por que este workshop usa CDK e não CloudFormation puro? Mesmo resultado final (CDK sintetiza para CloudFormation), mas com um nível de abstração em Java que reduz boilerplate e permite reuso via constructs — o trade-off é uma camada extra de build (Maven) entre o código e o template real que é de fato aplicado.

Próximos passos para produção

1. Habilitar SnapStart para Lambdas Java publicadas por alias

SnapStart reduz cold start (Módulo 2) em Lambdas Java inicializando a função no momento da publicação da versão e restaurando ambientes a partir de snapshot. Ele funciona em versões publicadas, não em $LATEST. Por isso, crie um alias, como live, e faça Step Functions ou event source mappings apontarem para esse alias quando aplicável.

Function eventRouter = Function.Builder.create(this, "OrderEventRouter")
        .runtime(Runtime.JAVA_21)
        .handler("com.example.OrderEventRouterHandler::handleRequest")
        .code(Code.fromAsset("../workflow-lambda/target/workflow-lambda.jar"))
        .snapStart(SnapStartConf.ON_PUBLISHED_VERSIONS)
        .build();

Alias eventRouterLive = Alias.Builder.create(this, "OrderEventRouterLive")
        .aliasName("live")
        .version(eventRouter.getCurrentVersion())
        .build();

Para funções chamadas pela Step Function, use o alias no LambdaInvoke. Para função consumidora de Kinesis, valide se o event source mapping está apontando para a versão/alias desejado.

2. Adicionar OpenTelemetry/ADOT para Honeycomb, e encaminhamento de log para Splunk

Use OpenTelemetry como padrão de instrumentação (Módulo 4) para traces e métricas. Para ECS, o caminho comum é Java Agent no container Spring Boot. Para Lambda, avalie ADOT Lambda Layer ou instrumentação manual. O Collector fica responsável por exportar traces/métricas para o Honeycomb — Splunk não faz parte desse caminho OTLP (ver abaixo).

OTEL_SERVICE_NAME=spring-api
OTEL_RESOURCE_ATTRIBUTES=deployment.environment=prod,service.version=1.0.0
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317
OTEL_TRACES_EXPORTER=otlp
OTEL_METRICS_EXPORTER=otlp
OTEL_LOGS_EXPORTER=none

Recomendação de produção: não coloque a chave do Honeycomb diretamente no container da aplicação. Configure-a no OTel Collector, usando Secrets Manager ou SSM, e permita que apps enviem OTLP apenas para o Collector.

Fonte de dados do Honeycomb (traces/métricas, via OTLP):
Spring Boot / Lambda -> OTLP -> ADOT/OTel Collector -> Honeycomb

Fonte de dados do Splunk (logs, via CloudWatch, não via OTLP):
Spring Boot / Lambda -> stdout/stderr -> CloudWatch Logs -> encaminhamento -> Splunk

Não deixe senha de banco, tokens, API keys ou endpoints privados hardcoded em application.properties. Use o arquivo para defaults não sensíveis e injete valores sensíveis em runtime.

4. Configurar autoscaling do ECS por CPU, memória e request count

Para APIs Spring stateless, escale horizontalmente aumentando o número de tasks. Comece com CPU/memória e adicione request count no ALB quando tiver tráfego real.

ScalableTaskCount scaling = service.getService().autoScaleTaskCount(EnableScalingProps.builder()
        .minCapacity(2)
        .maxCapacity(10)
        .build());

scaling.scaleOnCpuUtilization("CpuScaling", CpuUtilizationScalingProps.builder()
        .targetUtilizationPercent(60)
        .build());

scaling.scaleOnMemoryUtilization("MemoryScaling", MemoryUtilizationScalingProps.builder()
        .targetUtilizationPercent(70)
        .build());

scaling.scaleOnRequestCount("RequestCountScaling", RequestCountScalingProps.builder()
        .requestsPerTarget(1000)
        .targetGroup(service.getTargetGroup())
        .build());

Regras práticas: mantenha pelo menos duas tasks em produção, configure health check real em /health, use deployment circuit breaker, e monitore latência p95/p99 antes de aumentar agressivamente os limites.

5. Adicionar DLQ/on-failure destination para Lambdas e alarmes para falhas de Step Functions

Vale separar dois mecanismos que parecem a mesma coisa mas não são, porque as três Lambdas deste workshop são invocadas de duas formas diferentes:

  • OrderEventRouterHandler (Módulo 2/3) é acionada pelo event source mapping do Kinesis — um modelo pull, não uma invocação assíncrona. Para ela, o mecanismo de falha é o on-failure destination do event source mapping, não um DLQ "clássico" de Lambda.
  • ReserveInventoryFunction/AuthorizePaymentFunction/SendConfirmationFunction (Módulo 2) são invocadas de forma síncrona pelo LambdaInvoke do Step Functions — o addRetry/addCatch já cobre falha ali; um DLQ de invocação assíncrona da Lambda simplesmente não se aplica a essa integração.

Isso já resolve o cenário de "poison pill" citado na pergunta de entrevista da recapitulação: configure bisectBatchOnError, um retryAttempts finito e um destino on-failure no event source mapping do Kinesis, para que um registro problemático pare de bloquear o shard e caia em uma fila para investigação manual, em vez de re-tentar para sempre.

import software.amazon.awscdk.Duration;
import software.amazon.awscdk.services.sqs.Queue;
import software.amazon.awscdk.services.lambda.eventsources.KinesisEventSource;
import software.amazon.awscdk.services.lambda.eventsources.OnFailureDestinationProps;
import software.amazon.awscdk.services.lambda.destinations.SqsDestination;

// Fila para onde vão os metadados dos batches que falharam repetidamente
// (não o payload completo do Kinesis — só o suficiente para localizar o registro).
Queue eventRouterDlq = Queue.Builder.create(this, "OrderEventRouterDlq")
        .queueName("order-event-router-dlq")
        .retentionPeriod(Duration.days(14))
        .build();

eventRouter.addEventSource(KinesisEventSource.Builder.create(orderChanges)
        .batchSize(100)
        .startingPosition(StartingPosition.LATEST)
        .bisectBatchOnError(true)
        .retryAttempts(3)
        .onFailure(new SqsDestination(eventRouterDlq))
        .build());

Para o workflow de Step Functions, o addCatch do Módulo 2 já evita que uma execução trave, mas cair no estado OrderFailed silenciosamente não avisa ninguém — por isso vale um alarme no CloudWatch sobre a métrica de execuções falhas da própria state machine:

import software.amazon.awscdk.services.cloudwatch.Alarm;
import software.amazon.awscdk.services.cloudwatch.ComparisonOperator;
import software.amazon.awscdk.services.cloudwatch.MetricOptions;
import software.amazon.awscdk.services.cloudwatch.actions.SnsAction;
import software.amazon.awscdk.services.sns.Topic;

Topic opsTopic = Topic.Builder.create(this, "EcommerceOpsAlerts").build();

Alarm workflowFailedAlarm = Alarm.Builder.create(this, "EcommerceWorkflowFailedAlarm")
        .metric(stateMachine.metricFailed(MetricOptions.builder()
                .period(Duration.minutes(5))
                .statistic("sum")
                .build()))
        .threshold(1)
        .evaluationPeriods(1)
        .comparisonOperator(ComparisonOperator.GREATER_THAN_OR_EQUAL_TO_THRESHOLD)
        .alarmDescription("Uma ou mais execuções do EcommerceWorkflow falharam")
        .build();

workflowFailedAlarm.addAlarmAction(new SnsAction(opsTopic));

O mesmo padrão (metricFailed/metricTimedOut/metricAborted na state machine, com Alarm + ação SNS) serve para qualquer workflow Standard do Step Functions — não é específico deste e-commerce.
