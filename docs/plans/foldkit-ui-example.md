# Plan: a Foldkit UI for the course-enrolment app (tutorial step 5)

## Context
Effect 4.0.0 is out and the repo is on it (commit 2a6e86a); Foldkit 0.165.0 peer-requires exactly `effect@4.0.0` and `@effect/platform-browser@4.0.0`, so the two now line up. The earlier decision (see the project memory note) was to build a UI example only once both aligned. This plan adds `examples/course-enrolment-ui`: one page that drives the existing course-enrolment API, as a fifth and last step of the tutorial.

Why it is worth building. The page itself adds no framework feature; its value is the evidence it produces, and the follow-ups that evidence should drive (see "Findings" and "Follow-ups this should drive" below):
- It is the first real CLIENT of the HTTP API and the OpenAPI description. It shows what a consumer sees: `?waitFor` makes the next read correct without a polling loop, domain refusals arrive as typed problems with their own fields, and the response schemas can be reused.
- It exercises the gaps we expect and want to record honestly: untyped command routes in the derived client, no live updates, no per-field validation errors from the server.
- Foldkit and Crablet share a vocabulary (Schema everywhere, fact-named messages, events), so the tutorial can tell one story: the page's Messages are the same kind of thing as the server's events.

## What exists (verified)
- Foldkit 0.165.0 (npm): Elm-style `Model` / `Message` / `update` / `view` / `Command`, `Runtime.makeApplication`, `foldkit/http` (a Fetch-backed `HttpClient` Layer with trace-header propagation off so requests stay CORS-simple), `foldkit/fieldValidation` (per-field state: NotValidated / Validating / Valid / Invalid), `foldkit/asyncData` (Idle / Loading / Refreshing / Failure / Success / Stale), Story tests (`given` / `message` / `resolve`: drive `update` and resolve Commands inline, no mocks) and Scene tests (drive the real view with accessible locators, no browser). Scaffolding: `npx create-foldkit-app` (Vite plugin, Tailwind, Oxlint).
- The Story/Scene helpers are written for **vitest** (`foldkit/test/vitest` setup file); this repo tests with `bun:test` (unit) and `node:test` (integration).
- The course API (`examples/course-enrolment-app`): `POST /api/commands/define_course` and `/subscribe` (optional `?waitFor=course-seats-view&waitTimeout=`), `GET /api/courses/:courseId` returning `{ courseId, capacity, subscribers, seatsLeft }`; refusals are `application/problem+json`: a DOMAIN error carries `errorType` and the error's own `fields` only (`CourseNotFound`, `CourseFull`, `StudentAtLimit`), while the framework's 400 (`BadRequest`) and 409 (`Conflict`) problems carry `type`, `title`, `status` and `detail`; the success body is `{ status: "CREATED" | "IDEMPOTENT", reason, lastPosition, view?: { name, caughtUp, reason? } }`. `GET /openapi.json` serves the description.
- The view processor is woken by Postgres `LISTEN/NOTIFY` (the poll interval is only the fallback), so a view normally catches up within milliseconds: a read right after a write is stale only rarely, unless the view is slowed on purpose (the wait tests use a 400 ms polling view).
- The root `tsconfig.json` has `lib: ["ESNext"]` (no DOM) and includes `examples/*/src/**`; `test:unit` runs `examples/*/test/*.test.ts` under bun; `test:integration` runs `examples/*/test/integration/*.test.ts` under node. The tutorial-sync test resolves every `node <script>` line against the course app's directory, every `bun test <file>` against the repo root, and every `localhost:8080` URL against the checked-in OpenAPI routes.
- There is NO CORS handling in the server, and no list-courses endpoint. The derived client (`HttpApiClient.make(makeCourseApi())`) works in tests but is used as `any` (command routes are generated per command, not typed).
- `makeCourseApi` lives in `CourseApp.ts`, next to server-only imports (event-poller, views, Postgres): not importable from a browser bundle as it is.
- Workspaces are `examples/*`, so a new `examples/course-enrolment-ui` is picked up by `bun install`.

## Decisions
1. **A separate workspace package `examples/course-enrolment-ui`** (Vite + Foldkit + plain CSS, no Tailwind, to keep the example readable), kept OUT of the root checks that cannot handle a browser package:
   - **Typecheck**: it needs the DOM lib, the root config has none. The package has its own `tsconfig.json` (DOM lib) and a `typecheck` script; the root `tsconfig.json` does not include it (it lives under `src/` and `test/` like the others, so the root `include` globs get narrowed or an `exclude` for `examples/course-enrolment-ui` is added), and the root `typecheck` script chains the package's.
   - **Unit tests**: Story tests of `update` and Scene tests of the view, all under `bun:test` (the spike showed `foldkit/test` needs no vitest), in `examples/course-enrolment-ui/test/*.test.ts`, picked up by the root `test:unit` glob. The package needs the DOM lib only for `entry.ts`; the tests and `main.ts` do not touch the DOM.
2. **Same origin through the Vite dev proxy.** `/api` and `/openapi.json` proxy to `localhost:8080`, so the server needs no CORS code and the browser sees one origin. (Adding CORS to `commands-http` is a real product question; it is out of scope here and listed as a finding.)
3. **The page**, small on purpose: (a) "Define a course" form (id, capacity); (b) a course lookup that shows `capacity / subscribers / seatsLeft` from the read endpoint; (c) a "Subscribe a student" form; (d) a message area showing the outcome. Subscribing sends `?waitFor=course-seats-view` and, on `caughtUp: true`, does ONE read; the on-screen result is correct without polling. A toggle turns `waitFor` off. Because the view normally catches up in milliseconds, the stale read is only visible if the view is slow on purpose: the course app gets an opt-in `COURSES_VIEW_DELAY_MS` (default 0; when set, the seats projector sleeps that long before applying each event; documented in the tutorial as a demo knob, not production code). Without it the toggle would almost always show the right number and teach nothing; if the knob is rejected, the toggle is dropped and the page says only what `waitFor` guarantees.
4. **The page uses the API definition itself.** The spike showed that moving `makeCourseApi` out of `CourseApp.ts` into a browser-safe `src/CourseApi.ts` is cheap (+57 kB, no Node modules), so the UI imports it and derives its client with `HttpApiClient.make(makeCourseApi(), { baseUrl: "" })` instead of re-declaring the wire contract. What remains hand-written is only what the derived client cannot give: because command routes are generated per command the client is effectively `any` (the known gap), so the UI wraps the two command calls and the read in small typed functions that decode with the response Schemas the API already exports (`CommandCreatedResponse`, `CourseResponse`, `problemSchemaOf(...)`). If wiring the derived client inside a Foldkit Command proves awkward (it needs `HttpClient`, which `Http.layer` provides), the fallback is the three hand-written Schemas the first draft of this plan had.
5. **Tests**: Foldkit Story tests (Messages in, Model and Commands out, Commands resolved inline) for `update`, and Scene tests (click, type, assert text) for the real view, all under `bun:test`, no vitest (verified in the spike).
6. **Typed problems drive the UI**: a refusal Message carries the problem's `errorType` and `fields`; the view maps `CourseFull` to "course X is full (capacity N)", `StudentAtLimit` to "student X is already in 3 courses", and `CourseNotFound` to a message by the course field. The framework's 400/409 problems and anything unrecognised fall back to their `title` and `detail`. This is the "typed problems" demonstration.
7. **Per-field validation uses `foldkit/fieldValidation` on the client** (course id non-empty, capacity a positive integer) and the server's 400 problem is shown on the page as a general error, because the server does not report per-field errors. This is recorded as the gap it is.
8. **Tutorial step 5** in `docs/tutorial/course-enrolment.md` with tested `<!-- file: ... -->` blocks, like the other steps; README gets one line pointing at it. To stay compatible with `tutorial-sync.test.ts`: the UI is started with `bun run dev` / `bun run --cwd examples/course-enrolment-ui dev` (the test only resolves lines that start with `node <script>`), no `bun test <file>` line names a file that does not exist, and the only `localhost:8080` URLs are real OpenAPI routes (the Vite URL is `localhost:5173`, which the test ignores). The `\`blocks.length >= 10\`` check is unaffected.

## Spike results (phase 0 - done, 2026-10-01; scratch project outside the repo, nothing committed)
Setup: `foldkit@0.165.0` + `effect@4.0.0` + `@effect/platform-browser@4.0.0` + Vite 7, a one-input "look up a course" program (Model, `defineMessageUnion`, a `Command.define` with `Http.layer` and a Schema-decoded response, `update`, `view`).
- **(a) Story AND Scene tests run under `bun:test`.** `foldkit/test` (`Story.story`, `Story.Command.resolve`, `Scene.scene`, `Scene.click`/`type`/`role`/`text`) imports no test runner; only its optional matchers are written for vitest, and `expect.extend(Scene.sceneMatchers)` works under bun. A story with an unresolved Command, and a scene asserting text that is not there, both throw (negative controls pass). So **no vitest is needed**: decision 1's `vitest/` directory is dropped.
- **(b) The API definition can be shared with the browser; `CourseApp.ts` cannot.** Importing `makeCourseApi` from `CourseApp.ts` fails the Vite build (it drags in `@effect/sql-pg`, which needs `node:tls` and `node:crypto`). Composing the same API from only the pure modules (`commands-http/src/CommandApi.ts`, `ExposedCommand.ts`, the domain `Enrolment.ts`, `CourseQueryApi.ts`) builds cleanly: 328 kB (74 kB gzip) on its own, **+57 kB (+20 kB gzip)** on top of the Foldkit app (312 kB / 103 kB gzip), no Node modules. So moving `makeCourseApi` into a browser-safe `src/CourseApi.ts` (with `CourseApp.ts` importing it back) is a small, mechanical refactor.
- **(c) The program and its Commands run under plain Node with no DOM.** `main.ts` imports and the Command's Effect runs; two requirements: type-only imports must be `import type` (Node strips types but does not elide imports; the repo already follows this), and the relative URL needs a base, which `globalThis.location = new URL(baseUrl)` supplies (without it the Command returns its Failed Message and never calls `fetch`). Because `Http.layer` is provided inside the Command, a test cannot swap the HTTP client; the `location` base is how Phase 4 points the real Commands at a real server.
- **(d) The Vite dev proxy is transparent.** Query strings (`?waitFor=...&waitTimeout=...`), request bodies, status codes and `application/problem+json` bodies are forwarded unchanged.
- Not checked in the spike: the derived client's TYPES against a real server (the existing `course-http` test already uses it as `any`), and anything involving the real course app and Postgres (Docker was not running).

## Phase 1-2 results (what building it showed)
- **Refusals arrive as the API's own problems, and a domain error's class is enough to decode its body.** `Schema.Struct({ errorType: Literal(Error.tag), fields: Struct(Error.fields) })`, built from the domain error class's `tag` and `fields` statics, narrows the real response (`CourseFull` -> `{ courseId, capacity }`); no field is written twice. Verified against the real server on Postgres for: define (created), define again (the framework's `Conflict`, detail "Duplicate operation: \"define_course\" was already done"), subscribe (CREATED), subscribe again (IDEMPOTENT, reason ALREADY_SUBSCRIBED), `CourseFull`, `CourseNotFound`, `StudentAtLimit`, lookup, and lookup of a missing course.
- **The derived client validates requests with the server's own Schema before sending.** A capacity of 0 never reaches the network: the client fails with a `SchemaError` whose message names the field (`Expected a value greater than or equal to 1 at ["capacity"]`). The server's own 400 for the same payload says only `Invalid payload for command: define_course`. So the client side of the "no per-field errors" gap is already closed by the shared Schema; the server side is not. The page maps it to a `Mismatch` problem.
- **The command routes are typed `any`.** `client.commands.execute_<name>` accepts `{ params, query, headers, payload }` all as `any` (so even a correct call fails to typecheck without a cast). The page confines the single cast to `runCommand` in `src/api.ts`, narrowed to the call's shape, and decodes the response with the API's own `CommandCreatedResponse | CommandIdempotentResponse`. Leaving the `any` in place made the Command's Effect requirement `unknown`, which Foldkit rejects: the cast must not leak into the Effect type.
- **Foldkit pieces that worked as documented:** `Command.define` with `args` and `Http.layer`, `AsyncData.Schema`, `FieldValidation.Field/makeRules/validate/isValid`, Story and Scene tests under bun (24 tests in the package).
- **Process:** the local Postgres container stopped twice between sessions (the server then answers 500 with a `SchemaError: Missing key at ["type"]` in its log: the problem-building code expects a Postgres error shape it did not get). A page that talks to a server whose database is down shows "The server could not be reached", which is the right message for a 500 it cannot classify.

## Phase 3 results (read your own writes)
- **The demo knob works and is opt-in.** `COURSES_VIEW_DELAY_MS` (default 0) / `startCourseViews(id, { viewDelayMs })` holds each batch back before the projector's transaction opens (no database transaction waits). With 400 ms against a real server, measured through the page's own Commands: a define that waits answers in ~527 ms and the read-back is right (3 left, 0 subscribed); a subscribe that does not wait answers in 14 ms and the read-back is stale (still 3 left, 0 subscribed); the next subscribe that waits answers in ~446 ms and the read shows 1 left, 2 subscribed (it includes the earlier one: the view's cursor passed both). A define that does not wait is not in the seat map at all yet: the read-back is a 404 `CourseNotFound`.
- **Without the knob the staleness is almost never visible** (the view is woken by LISTEN/NOTIFY and catches up in milliseconds), which is the right default and the reason the knob exists. A test (`course-view-delay.test.ts`) pins all four behaviours.
- **A stale 404 reads as a lie.** "There is no course called X" right after "Defined course X" is true of the seat map and false of the course. The page remembers the course it just wrote (`justWrote`) and turns that one 404 into "was just written, but the seat map has not caught up yet"; a lookup the user types themselves keeps the plain message. Worth a sentence in the tutorial: a view is a different thing from the truth, and an error from it is about the view.
- **`view` in the response is a first-class outcome, not an error.** `caughtUp: true`, or `false` with `timeout` / `view_failed` / `unavailable` / `nothing_appended` (an idempotent repeat), each with its own sentence on the page.
- 30 UI tests (Story, Scene, pure) under bun.

## Phase 4 results (the page against the real server, in the suite)
- `examples/course-enrolment-ui/test/integration/page-against-server.test.ts` (node:test, Testcontainers) starts the real course app with the seats view held back 300 ms and drives the page's OWN `update` with the page's OWN Commands (real derived client, real `fetch`) through a ten-line driver that plays Foldkit's runtime: feed a Message to `update`, run each Command it returns, feed the result Messages back, stop when nothing is left. What it ends with is the Model the page would show. Seven cases: define then read back; waiting off is stale / waiting on is right (and really waits); an idempotent repeat; every refusal (`CourseFull` with its capacity, `CourseNotFound`, `StudentAtLimit` with its limit, the framework's duplicate-course conflict); a lookup of a never-defined course vs. a just-written one; the page's validation and the derived client's `Mismatch` naming the field; an unreachable server.
- **No browser, no DOM, no mocks** - and no `contract.ts` fallback was needed: per the spike, `globalThis.location` supplies the base URL a browser would, and the test restores it afterwards.
- The test is cheap (about 7 s after the container starts) and is picked up by the existing `test:integration` glob; the UI's pure tests are picked up by `test:unit`.

## Findings the example should surface (and the tutorial should say plainly)
- Command routes are generated per command, so the derived client needs `any` (or hand-written Schemas); a typed client would need the command route names in the API type.
- No live updates: a second browser tab does not see a subscription until it reads. Views are asynchronous; there is no push channel.
- The server reports one 400 problem, not per-field errors, so the client validates the fields itself.
- No CORS in `commands-http`; the example uses a proxy.
- No `GET /courses` list endpoint, so the page needs the id up front.

## Follow-ups this should drive
Each finding above is a product question, not a UI fix; the example should end with them ranked, so it leads to work instead of staying a demo:
1. **A typed client for commands** (the derived client is `any` today): expose the command route names/types in the API type. Highest value for any consumer.
2. **Optional CORS in `commands-http`** (an allow-list option on the group layer), so a browser app on another origin needs no proxy.
3. **A built-in list/search read pattern** (or at least a documented one) so UIs are not given ids by hand.
4. **Per-field validation problems from the server**: the derived client already reports the failing path (`SchemaError`); the server's 400 should carry the same paths (`Invalid payload for command: define_course` today), so non-TypeScript clients get them too.
   (Related: a server whose database is down answers a 500 whose log line is a `SchemaError` from building the problem body, not the Postgres error: worth a look.)
5. **Live updates** (SSE or a "view changed" notification) - a larger design question; record, do not build.
None of these is in scope here; each becomes its own plan if chosen.

## Risks
| Risk | Mitigation |
|---|---|
| Foldkit is beta ("breaking changes may occur in minor releases") | pin the exact version (as ADR-0009 does for Effect); the spike and the tests catch drift on upgrade |
| Importing the API definition drags server code into the bundle | spike (b): `CourseApp.ts` does (sql-pg needs `node:tls`); the pure composition does not. The refactor moves only `makeCourseApi` and its inputs into `CourseApi.ts`, and a test in the UI package builds that module with Vite so a server import cannot creep back in |
| The UI package breaks the root `typecheck` / `test:unit` | decision 1: own `tsconfig` with the DOM lib and its own `typecheck` script (chained from the root), excluded from the root `include`; its tests are pure bun tests and run in the root `test:unit` |
| The stale-read demo does not show staleness (the view catches up in milliseconds) | the opt-in `COURSES_VIEW_DELAY_MS` knob (decision 3), tested; otherwise the toggle is dropped |
| Step 5 breaks `tutorial-sync.test.ts` | decision 8: `bun run dev` instead of `node <script>`, existing files only, `localhost:8080` URLs that are OpenAPI routes |
| Phase 4 depends on `globalThis.location` as the base URL | verified in the spike; it is a documented Web convention (a relative URL resolves against the page), and the test sets it back after each run |
| Scope creep into a styled app | decision 1: plain CSS, one page, four interactions; Tailwind, routing and submodels are non-goals |
| The browser is not driven in CI | the end-to-end node test covers the contract; a manual browser pass is recorded in the verification list |

## Verification
`bun run typecheck` (root and the UI package's own); `bun run test:unit` (the `update` tests and the tutorial-sync test); `vite build` of the UI package; `bun run test:integration` (the end-to-end contract test); `vite build` succeeds. Manual: `docker compose up -d`, `node src/migrate.ts`, start the server, `bun run dev` in the UI package, define a course with capacity 1, subscribe two students (the second shows "course is full"), toggle `waitFor` off to see a stale read.

## Non-goals
Routing, auth, styling beyond the basics, server rendering, a list/search endpoint, live updates, CORS in `commands-http`, a second UI for the wallet app, and any change to the course app's behaviour (a small refactor to move `makeCourseApi` is allowed only if the spike justifies it).
