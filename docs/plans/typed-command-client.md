# Plan: a typed command client - put the commands in the API's type

## Context
The Foldkit page (examples/course-enrolment-ui, tutorial step 5) is the first real client of the HTTP API, and its biggest friction is one cast. The client is derived from the API definition (`HttpApiClient.make(makeCourseApi())`), and the read endpoint comes out fully typed (`client.courseQueries.getCourse({ params })` returns a `CourseResponse`, fails with a typed problem), but the command routes come out as `any`:

```ts
// examples/course-enrolment-ui/src/api.ts - the one cast
const call = (client.commands as unknown as Record<string, CommandCall>)[`execute_${name}`]!;
```

Typing `client.commands.execute_define_course({ payload })` would give every consumer, not only this page: a payload checked at compile time (a typo in `capacity` fails to build), a success type (`CommandCreated | CommandIdempotent`), and an error channel made of the problems that command can answer with (`CourseNotFound | CourseFull | StudentAtLimit | BadRequest | Conflict`) plus the client's own `HttpClientError` (transport) and `SchemaError` (a request or answer that does not match the Schema; the page shows these as `Unreachable` and `Mismatch`). A match over those three groups is exhaustive, and the page's `Schema.is` guesses go away.

The runtime does not change at all. Only types do, so the generated OpenAPI description must stay byte-identical (the existing test checks that).

## What exists (verified)
- `makeCommandApiGroup(basePath, commands, options)` (`packages/commands-http/src/CommandApi.ts`) builds the group in a loop over a `Record<string, ExposedCommand<any, any>>` and returns `HttpApiGroup<"commands", any>`: "the one deliberate type-erasure", because the endpoint names are runtime strings. Endpoint ids are `execute_<commandName>` (`executeEndpointName`), paths `${basePath}/${commandName}`.
- `Command<In, Err>` (`packages/commands/src/Command.ts:90`) keeps only the DECODED input type and the union of error INSTANCE types. It declares `input: Schema.Constraint` and `errors: ReadonlyArray<AnyDomainErrorClass>`: the input Schema's own type and the tuple of error classes are lost at the type level, though `defineCommand` has both (`I extends Schema.Constraint`, `const Es extends ReadonlyArray<AnyDomainErrorClass>`).
- Effect's `HttpApiEndpoint<Id, Method, Path, Params, Query, Payload, Headers, Success, Error, ...>` takes Schema TYPES (`Payload extends Schema.Top`, `Error extends Schema.Top`), so a typed endpoint needs the input Schema's type and a Schema type per error problem; `HttpApiClient.Client<Groups>` then derives each method from them. That is why the read endpoint is typed (declared with its Schemas in plain sight) and the commands are not.
- A command's problem body (`problemSchemaOf(error)`, `ProblemDetail.ts`) is built at runtime from the error class's statics `tag`, `kind`, `fields`; its status/title come from `kind`. `DomainErrorClass<Tag, F>` carries `Tag` and `F` in its type, but `kind` is `ErrorKind` (a union), not a literal per class.
- Callers declare the registry with an annotation that erases the keys: `const walletCommands: Readonly<Record<string, ExposedCommand<any, any>>> = {...}` (wallet app, course app's tutorial `expose` region, two tests). Keys must stay literal for the group to know its endpoint names.
- The server side, `makeCommandApiGroupLive(api, commands, config)`, already takes `commands: Readonly<Record<string, ExposedCommand<any, any>>>` and builds its handlers through `HttpApiBuilder.group as any` ("narrow, deliberate type-erasure at this one dynamic-composition boundary"), returning `Layer<HttpApiGroup.Service<ApiId, "commands">, ...>`. It does not depend on the group's endpoint types, so a typed group cannot break it.
- Effect's client method type is `Effect<Success, E | HttpClientError | Endpoint["~Error"]["Type"] | SchemaError, R>` and its request type requires a `query` key whenever the endpoint's Query type is not `never` (our `waitQuery` is, with only optional fields): callers keep passing `query: {}`, as the page does today.
- Checked by search: every place that names `Command<A, B>` or `ExposedCommand<A, B>` is a generic parameter position that accepts any command (the executor, `Scenario.when`, automations, the audit, `inputJsonSchema`, the registry types) and stays assignable when the new parameters default to today's types.
- TypeScript here is 7.0.2 (the native compiler); a mapped-type union over a registry of five commands (wallet) is small, but the generic machinery should be checked for compile time.

## Decisions
1. **Carry the input Schema and the error classes in the type.** `Command<In, Err, I = Schema.Constraint, Es = ReadonlyArray<AnyDomainErrorClass>>` with `input: I` and `errors: Es`; `ExposedCommand<T, E, I, Es>` likewise. The extra parameters DEFAULT to today's erased types, so every existing use (`ExposedCommand<any, any>`, helpers that accept any command) compiles unchanged and `defineCommand` simply returns the more precise type.
2. **`makeCommandApiGroup` becomes generic over the registry**: `<const C extends Registry>(basePath, commands: C, options)` returns `HttpApiGroup<"commands", ListEndpoint | CommandEndpoints<C>>`, where `CommandEndpoints<C>` maps each key `K` to `HttpApiEndpoint<`execute_${K}`, "POST", `${string}/${K}`, never, WaitQuery, C[K]["command"]["input"], never, CommandCreatedResponse | CommandIdempotentResponse, ProblemsOf<C[K]>>`. The loop body does not change; the return statement asserts the precise type (the single remaining cast, now at one place and documented as "the runtime loop builds exactly this").
3. **Problem Schema TYPES are structural, not literal.** `ProblemsOf<...>` is `BadRequest | Conflict | Unexpected | ProblemBody<Tag, Fields>` for each declared error, where `ProblemBody<Tag, F>` is `{ type: string; title: string; status: number; detail: string; errorType: Tag; fields: Schema.Struct.Type<F> }`. It is wider than the runtime literals for `title`/`status` (the class does not carry a literal `kind`), which is honest and enough: the useful discriminant is `errorType`, and `fields` is exactly typed. The runtime Schemas (and the OpenAPI) are unchanged.
4. **The registry must keep its keys.** `Readonly<Record<string, ExposedCommand<any, any>>>` annotations are replaced by `satisfies Registry` (or no annotation) in the wallet app, the course app (and the tutorial's `expose` block, which is a tested file region), and the tests. The tutorial gets a one-line explanation ("do not annotate the registry as a `Record<string, ...>`: that forgets the command names").
5. **Fallback if the generic endpoint type does not infer cleanly with Effect's `HttpApiEndpoint`**: keep `HttpApiGroup<"commands", any>` and ship a thin typed facade in `commands-http` instead, `typedCommandClient<C>(client)` returning `{ [K in keyof C]: (payload: In<C[K]>, options?) => Effect<Outcome, ProblemsOf<C[K]>> }`. Worse (a second client API next to the derived one) but needs only decision 1 and no Effect type gymnastics. The spike decides which.
6. **Type-level tests are real tests.** A compile-checked file, `packages/commands-http/test/typed-client.types.ts` (under the root `include`, which has `packages/*/test/**/*.ts`; not matched by the `*.test.ts` globs, so no runner tries to execute it) with `// @ts-expect-error` lines and small `Expect<Equal<...>>` helpers, fails `bun run typecheck` if the types regress: a misspelled payload field, an unknown command name, an error that was not declared, and the exhaustiveness of a `switch` over `errorType`.
7. **The page loses its cast and its guesses.** `runCommand` calls `client.commands.execute_<name>({ payload, query })` directly; `problemFromError` becomes a match over `HttpClientError | SchemaError | <the command's typed problems>` (no `Schema.is` probing, no `as unknown as`; the problems are told apart by `errorType`, the framework's 400/409 by their `title`/`detail`). A type-level check in the UI package ties the two together: for each command the page calls, the tags of its declared domain errors must all be tags of the page's `Problem` union (a `satisfies`-style assertion over `typeof Subscribe`'s error classes), so declaring a new error on the server without the page handling it fails the page's typecheck.

## Phases (each ends green: `bun run typecheck`, `bun run test:unit`, `bun run test:integration`; commit per phase; push only on request)
### 0. Spike (0.25 day) - decides 2 and 5
In a scratch directory (not committed), against the real packages: (a) give `Command`/`ExposedCommand` the two extra type parameters and check `defineCommand`/`exposedCommandOf` infer the precise `I` and `Es`; (b) write `CommandEndpoints<C>` and a generic `makeCommandApiGroup` signature and check that `HttpApiClient.make(HttpApi.make("x").add(group))` gives `client.commands.execute_subscribe` the expected parameter and error types, with `const` inference of the keys; (c) check the compile time of `tsc` on the wallet app (5 commands) before and after; (d) check that the places that consume the API TYPE accept the typed group: `HttpApiBuilder.layer(api, ...)`, `OpenApi.fromApi(api)` (the docs generation and its test) and `HttpApiClient.make(api)`. (`makeCommandApiGroupLive` is already cast with `as any` and cannot break.) Record the answers here; if (b) fails, take the fallback in decision 5.
### 1. The commands carry their types (0.5 day)
Decision 1 in `packages/commands` and `packages/commands-http`; defaults keep everything compiling; no runtime change. Type tests for `defineCommand`'s result (input Schema type and error tuple preserved).
### 2. The typed group (0.75 day)
Decisions 2 and 3 in `makeCommandApiGroup`/`makeCommandApi`; the registry annotations in the wallet app, the course app, the tutorial block and the tests (decision 4); the type-level test file (decision 6). The OpenAPI unit test and both generated documents must be unchanged; all integration suites stay green.
### 3. The consumers (0.5 day)
The course UI (decision 7): delete the cast, type the error channel, make the problem match exhaustive, adjust its tests; the `course-http` integration test's `client: any` becomes the typed client with its assertions on typed errors. README and tutorial step 3/5 text and blocks follow the code; ADR-0011 gets a short addendum (the group's type is no longer erased); NOTES entry.

## Risks
| Risk | Mitigation |
|---|---|
| Effect's `HttpApiEndpoint` generics do not accept the computed union cleanly (inference blow-ups, "excessively deep" errors) | spike (b); the facade fallback (decision 5) needs no endpoint types |
| `const` type parameters infer literal keys only for object literals written at the call site; an app that builds its registry elsewhere loses them | the registry is a plain object literal in every example; documented in the tutorial (decision 4); a non-literal registry degrades to today's `any`-ish client, not to a compile error |
| Callers that annotate the registry as `Record<string, ...>` silently lose typing | the tutorial and ADR addendum say so; the type test pins a literal registry; no compile error is possible for the erased case, so the examples are the guard |
| `Command` gains two type parameters: breaking for code that names `Command<A, B>` | the new parameters have defaults equal to today's types; checked: every use in the repo is a generic position that accepts any command and stays assignable (covariant `readonly` members) |
| Compile time on bigger registries | spike (c) measures the wallet app (5 commands); a threshold is recorded before committing to the approach |
| Types drift from the runtime (the type says an error the loop does not add, or vice versa) | the integration tests run the typed client against the real server for each declared error; the `errors` list is the single source for both the runtime Schemas and the type |

## Verification
`bun run typecheck` (including the type-level tests, whose `@ts-expect-error` lines FAIL the build if the types become permissive again); `bun run test:unit`; `bun run test:integration`; the OpenAPI documents unchanged (`git diff docs/api` empty after `bun run docs:api`); `vite build` of the UI package; the course UI integration test still passing with `runCommand` calling the typed method. Manual: in the editor, hovering `client.commands.execute_subscribe` shows the payload and the error union.

## Non-goals
Changing any route, status code or response body; generating clients for other languages; typed `?waitFor` view names (the query stays `Schema.String`, validated at runtime, as documented); typing the READ side beyond what already works; the other follow-ups (CORS, list endpoint, server-side per-field validation problems, live updates), each its own plan.

## Size
About 2 days: spike 0.25, commands carry their types 0.5, typed group 0.75, consumers and docs 0.5. If the spike forces the facade fallback, about 1.5 days.
