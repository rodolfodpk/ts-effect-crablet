# Plan: the API follow-ups the Foldkit page surfaced (seven items, ranked)

## Context
The Foldkit page (examples/course-enrolment-ui, tutorial step 5) was the first real client of the HTTP API, and the typed command client closed its biggest gap. What is left are product questions, each small enough to be its own piece of work. They come from two places: the findings recorded in NOTES.md ("Course UI") and the design discussion about one definition with two consumers (OpenAPI for any language, Foldkit for TypeScript + Effect). The recommendation from that discussion is the frame for everything below: **keep one definition and one transport; specialize only at the edges** (the contract/logic boundary, UI-only endpoint groups, CORS, and different evolution rules for the public projection).

## A. The server's 400 names the failing fields
**Verified.** `defineCommand`'s `decodeInput` turns a `SchemaError` into `InvalidInput({ message })` (`packages/commands/src/Command.ts:158`), and `CommandApiLive` then discards even that and answers a fixed `Invalid payload for command: <name>` (`CommandApiBadRequest.of`). The derived TypeScript client validates the same Schema before sending and its `SchemaError` names the path (`at ["capacity"]`); every other client (curl, Python, the generated OpenAPI clients) gets nothing to act on. Effect's `SchemaIssue.makeFormatterStandardSchemaV1` produces `{ message, path }` issues from a `SchemaError`.
**Decision.** The 400 problem gets an `errors` extension member (RFC 7807 allows them): `[{ path: ["capacity"], message: "..." }]`, built from the `SchemaError` issue. `InvalidInput` carries the structured `issues` next to `message`. `CommandApiBadRequest` gains an optional `errors` field, so the generated OpenAPI changes **additively** (policy B). The page shows the messages under the matching form field.
**Privacy is a requirement, not a detail.** Schema messages can echo the received value ("Expected a value greater than or equal to 1, got 0"); the repo has personal-data markers and redaction (Privacy P1-P3). The 400 must never echo input values: messages are built from the failed check's description and the path only, or run through the existing redaction; a test pins that a personal field's value does not appear in the body.
**Phases.** (1) `InvalidInput.issues` + the extraction + unit tests, including the no-echo test; (2) the problem body, the OpenAPI document (regenerate; additive), the integration test (`errors[0].path` is `["capacity"]`); (3) the page: `Rejected` shows per-field messages and marks the fields; tutorial step 5 text; NOTES.
**Risks.** Path representation for nested/array inputs (use the formatter's path as is, document it); a message leaking a value (the no-echo test); clients that parsed the old fixed `detail` (it stays unchanged).

## B. Evolution rules for the OpenAPI projection
**Verified.** `docs/api/*.json` are checked in and a unit test fails on **any** difference between the generated document and the snapshot (`course-openapi.test.ts`, the description tests). That is a drift alarm, not a compatibility alarm: an additive change and a breaking one fail the same way, and nothing records which kind it was. The path prefix is configurable (`basePath`, default `/api/commands`); nothing is versioned.
**Decision.** A written policy (an ADR) and a test that enforces it:
- *Additive* (always fine): a new route, a new optional request field, a new response field, a new declared problem, a new enum value on a response.
- *Breaking* (needs a new version): removing or renaming a route, a field, a problem or a status; a new required request field; narrowing a request type; widening a response type clients switch on.
- The public projection is **frozen per version**: once an external consumer exists, `docs/api/<name>-v1.json` is the committed contract and a test fails if the generated document is *breaking* relative to it (additive passes and asks for the snapshot to be regenerated). Versioning is by path prefix, set through the existing `basePath` (`/v1/commands`), because it needs no new mechanism. Co-deployed UIs do not need this: they track `main`.
**Phases.** (0) A small spike: classify differences between two OpenAPI documents with an existing tool (for example `oasdiff` or a Node library) or a ~100-line structural diff over the parts we generate (paths, request/response schemas, problems) - pick the cheaper that is reliable; (1) the ADR and the policy text in the README's API section; (2) the frozen-snapshot test, wired to the course API as the worked example, with a deliberately breaking change checked to fail it.
**Risks.** A diff tool that misclassifies (the spike measures it on real changes made in this repo's history, for example the `view` field added to responses); freezing too early (the policy says "freeze when the first external consumer exists", not now).

## C. Optional CORS in `commands-http`
**Verified.** The server has no CORS handling; the page uses a Vite proxy. Effect provides `HttpMiddleware.cors({ allowedOrigins, allowedMethods, allowedHeaders, exposedHeaders, maxAge, credentials })`. Gotcha in Effect's own docs: middleware passed to `HttpRouter.serve({ middleware })` wraps the whole server chain and **changes to the response are not reflected**; response-modifying middleware (CORS adds headers) must go through `HttpRouter.middleware`. The apps compose their own router (`HttpRouter.serve(makeCourseApiLayer(...))`), so the right shape is a helper the app opts into, not behaviour inside the group.
**Decision.** Export a `corsLayer(options)` (router-level middleware, deny-by-default: no option, no CORS headers) from `commands-http` with sensible defaults for this API (`exposedHeaders: ["X-Correlation-Id"]`, the methods and headers the routes use, `maxAge`), documented as "needed only when the UI is on another origin". The UI gets a `VITE_API_URL`-style base URL so it can run without the proxy; the proxy stays the default dev setup.
**Phases.** (0) Spike: `HttpRouter.middleware` + `HttpApiBuilder.layer` + the docs layer compose, and the preflight (`OPTIONS`) reaches the middleware; (1) the helper + docs; (2) integration test: an allowed origin gets `Access-Control-Allow-Origin` and the preflight succeeds, a disallowed origin gets no CORS headers, `credentials: true` with a wildcard origin is rejected at construction; (3) the page runs against the server on another port without the proxy.
**Risks.** A wildcard with credentials (rejected by construction); CORS middleware ordering against error responses (the test covers a 4xx and a 5xx from the API).

## D. A list/search read pattern
**Verified.** Both apps write their read endpoints by hand (course: one, `getCourse`; wallet: three) as an `HttpApiGroup` plus a `...Live` implementation over the app's own view tables; there is no list or search endpoint, so the page asks for a course id. No generic query machinery exists, and one is not warranted by two apps.
**Decision.** No query engine. (1) Add `GET /api/courses` to the course app: a keyset-paginated list over `course_seats_view` (`?limit=` bounded, `?after=<courseId>` cursor, optional `?q=<prefix>`), response `{ items: [...], next: string | null }`; parameterized SQL, no offsets. (2) The page gets a course picker fed by it, refreshed after each write (read-your-writes applies to the list too). (3) Extract a small `Page(Item)` response Schema and cursor helpers into `@crablet/views` **only if** the wallet app needs a list as well; otherwise they stay in the course app and the pattern is documented, not abstracted.
**Phases.** (1) The endpoint, the SQL, the OpenAPI document (additive), integration tests (ordering, limit bounds, `after`, `q`, empty); (2) the picker in the page + Story/Scene tests + the end-to-end test; (3) tutorial text and, if (3) above triggers, the extraction.
**Risks.** Premature abstraction (the "only if the wallet needs it" rule); unbounded `limit` (clamped and tested); `q` as a `LIKE` pattern (escape `%`/`_`).

## E. Live updates: a view-change feed
**Verified.** The only notification today is `pg_notify('crablet_events')` when events are appended, which wakes the pollers; **nothing signals that a view has applied events**, so a client cannot know when a read has become fresh except by `?waitFor` (a held request) or by polling. Effect 4.0.0 has `HttpApiSchema.StreamSse` and an `Sse` codec, and `HttpApiClient` types SSE endpoints; Foldkit turns a stream into Messages with a Subscription (`Subscription.make`, `persistent`). Progress is now a `(transaction_id, position)` cursor (ADR-0012), which is exactly what a client holding its write's marker needs to compare.
**Decision.** A **ping, not data**: the feed says "view V advanced to cursor C"; the client re-reads. No row data crosses the feed (nothing to authorize or leak beyond a view name and a cursor; auth is a later, separate concern).
- *Source.* After the poller commits a view's progress update (`updateCursor`), `pg_notify('crablet_view_progress', '<view>|<xid>|<position>')`, **outside** the projection transaction (so a ping never precedes visibility) and best-effort (at-most-once is fine: clients re-read on every ping and on reconnect). The notify belongs to the poller package that owns the progress table.
- *Transport.* One endpoint, `GET /api/views/changes?views=a,b` (SSE), in a separate group/package (`views-http`), not in `commands-http`; coalesces bursts, sends a heartbeat comment, closes on server shutdown. One multiplexed connection per page (browsers cap HTTP/1.1 connections per origin).
- *Client.* A Foldkit Subscription over the stream emits `ViewAdvanced { view, cursor }`; `update` re-reads the open course when the cursor reaches the page's own write marker (the same comparison `waitUntilProcessed` makes) or when any ping arrives for the watched view. `?waitFor` stays as the request-scoped way.
**Phases.** (0) Spike: an `HttpApi` SSE endpoint through the Vite proxy (buffering?), decoded in the browser (the derived client's stream vs `EventSource`), a Subscription feeding Messages; (1) the notify after `updateCursor` + a poller integration test (a ping per advance, none on a failed batch); (2) the feed group + a server integration test (subscribe, write, receive a ping whose cursor covers the write; heartbeat; clean close); (3) the page: Subscription, Story tests for the Message, the two-tab demonstration; (4) docs, NOTES, an ADR for the signal (why a ping, why after commit, at-most-once).
**Risks.** Proxies and compression buffering SSE (the spike); many views x many clients (one `LISTEN` shared per process, fan-out in memory); reconnect storms (client backoff via Foldkit; the server does not replay, the client re-reads); a notify lost on a crash (re-read on reconnect covers it).

## F. Contract vs logic
**Measured (corrects an earlier claim).** `bun build` of the page with a metafile: of 398 kB (minified), `effect` is 206 kB and Foldkit 158 kB; the course domain, the command pipeline and the event-store error types that the API definition drags in are **about 15 kB (under 4%)**. The split is therefore **not** about bundle size. It is about exposure:
- **Not an authorization hole.** The server stays the authority: the browser only sends HTTP, and `decide` runs in the server's executor against the real store; a copy of the code gives a client no power.
- **An exposure and hygiene problem.** `CourseApi.ts` imports the domain, so `decide`, the models and the event definitions (business rules, thresholds, event names, the tags that draw the consistency boundaries, `idempotentBy` queries) ship to the browser by default. A domain module that one day imports something server-only (config, a database client, Node's `crypto`) would break or poison the browser build or leak into it. "Shipped unless someone remembers to stop it" is the wrong default, and the migration gets bigger with every command and example added. So it is scheduled, not left to a trigger.
- **CI gap.** CI runs typecheck (including the UI's), unit tests and integration tests, but never builds the UI.

**Design.** A command splits into two parts that are already separable:
- the **contract** - `name`, `input` Schema, `errors` (and with them the domain error classes): public, browser-safe, already published by the OpenAPI document;
- the **behavior** - `model`, `decide`, `prepare`, `idempotentBy`, `retries`, `consistency`, ...: server-only.

`defineCommand` does not change. `commandContract({ name, input, errors })` returns a typed plain object that preserves the literal types (the `const` input Schema type and the `errors` tuple), and the server spreads it: `defineCommand({ ...SubscribeContract, model, decide })`, which yields the same `Command<In, Err, I, Es>` as today.
- *Files.* `domain/enrolment.contract.ts` (no server imports; the error classes live here) and `domain/Enrolment.ts` (events, models, behavior; imports the contract). A command that is never exposed (like `SendWelcomeNotification`) needs no contract and stays single-file.
- *The API definition* (`CourseApi.ts`) registers **contracts** (`exposedContract(SubscribeContract)`); `makeCommandApiGroup` accepts anything with `{ name, input, errors }`, so an existing `Command` is still accepted and the split is opt-in per command. The typed client is unchanged (same `I` and `Es`).
- *The server* (`CourseApp.ts`) passes **implementations** to `makeCommandApiGroupLive`; a type (`Implements<typeof contracts>`) ties the two registries together, so a contract with no implementation, or a mismatched name, is a compile error: every route has code behind it.
- *The OpenAPI document* depends only on contracts, so it could be produced without loading any behavior.

**Effect on writing code.** Server: an exposed command is declared in two places (contract, then behavior); scenario tests, the executor and automations are untouched; events and models do not move. UI: no change to the code written (it already imports `course-enrolment-app/CourseApi` and uses the typed client); the bundle simply stops carrying `decide`, the models and the events. Costs: one more concept in tutorial step 3 ("the contract is the public part"), a naming/placement convention, and edits to the two examples, `exposed-command.test.ts` and the tutorial's `expose` block.

**Phases.**
- *Guard (0.25 day, ships with A, before the split).* A unit test that bundles `CourseApi.ts` for the browser (`Bun.build`/`bun build --target browser` with a metafile) and fails if the build fails or the output references `node:` modules or `pg`; with a negative control. Runs in CI through `test:unit`. After the split it is tightened (below).
- *0. Spike (0.25 day).* (a) `commandContract` preserves the `errors` tuple and the input Schema type, and `defineCommand({ ...Contract, ... })` is `Equal` to today's `Command` type (a type test); (b) `makeCommandApiGroup` accepts contracts and commands alike, the typed client and the generated OpenAPI document are byte-identical; (c) `makeCommandApiGroupLive` + `Implements<C>` give the compile error for a missing or mismatched implementation; (d) the metafile of a contract-only `CourseApi.ts` contains none of `Enrolment.ts`, `decide`, models or events, and by how much the bundle shrinks; (e) the guard runs in-process under `bun test` fast enough.
- *1. Core (0.5 day).* `commandContract`, `exposedContract`, the group/Live signatures, `Implements`, type tests (with controls), backward compatibility pinned by a test that still registers a `Command`.
- *2. The course app (0.5 day).* Split `Enrolment.ts`; `CourseApi.ts` registers contracts, `CourseApp.ts` implementations; the guard is tightened to fail if the browser bundle contains anything from the server-side domain module; OpenAPI documents unchanged; the UI package unchanged and its tests green; the tutorial's `expose` block and step 3 text follow.
- *3. The wallet app and docs (0.5 day).* Same split for the five exposed commands; README, an addendum to ADR-0010/0011, NOTES.
**Risks.** `const` generics lose the tuple through the spread (spike (a)); two registries drifting (the `Implements` type); a contract file quietly importing a server module (the tightened guard); more ceremony for small apps (single-file `defineCommand` remains for commands that are not exposed, and the split is opt-in for exposed ones).

## G. Foldkit server rendering (SSR/SSG) - an optional spike
**Verified.** Foldkit renders the same program on the server and hydrates it in place: static generation at build time or per-request rendering, under `foldkit/experimental/server` (the word "experimental" is Foldkit's own; Foldkit itself is beta). Its SSR example runs on an Effect HttpServer, which is what the course app already is, and initial data travels as serialized "flags" embedded in the HTML. Our own evidence: the integration test already imports the page's `main.ts` and runs its real Commands under plain Node with no DOM, so the program is server-safe in the sense that matters first (no DOM at import, Commands runnable). Not tried: rendering `view` to HTML and hydrating it.
**What it would and would not buy.** It would give a first paint that already contains data (a course catalog), indexable/link-previewable public pages, no loading flash, a page and an API from one deployable, and a literally isomorphic program (the same `update` and `view` on both sides, the same typed client fetching the data). The current page is an interactive tool with no SEO need, so it gains almost nothing today, and there is nothing worth rendering until the list endpoint (D) exists.
**Costs and risks.** An experimental API on a beta framework; hydration mismatches (the Model rendered on the server must equal the client's starting Model); how the server fetches its data (the typed client over HTTP, or the view queries in process) - either reads the lagging views, so a render can be slightly stale; hydration is not covered by Scene tests, so it needs its own test; more surface in the course app (a render route, a server entry); auth/cookies are a later concern. No conflict with F: the renderer is server code and may import the behavior; the browser bundle stays contract-only.
**Decision.** Spike first, commit later. No adoption work is scheduled.
**Spike (0.5 day, after D and F).** Answer four questions in a scratch worktree and record them here: (1) does Foldkit's SSR pattern work with our Model and Commands - init data via flags, or the init Commands resolved on the server - and what does `init` look like for each; (2) can the course app serve the page from its existing router (`/` and `/courses` next to the API, one process) without disturbing the API routes or the OpenAPI document; (3) does hydration keep the Model and the page's Subscription (E's feed, if it exists by then) working after the first paint; (4) does a server-rendered catalog page (from D's list endpoint) come out with the data in the HTML, and what is the cost of the extra server dependency in the bundle. Outcome: either a follow-up plan with phases (a render route, a hydration test, tutorial step 6) or a note here that it is not worth it yet.

## Order and dependencies
`A + F-guard` -> `B` -> `C` -> `D` -> `F (the split)` -> `E`; `G` (spike) after D and F, any time. F is scheduled before E on purpose: it is a rename-and-move migration that gets more expensive with every command and example added, while E adds new surface that should be built on the final contract/behavior layout. A and B change the generated OpenAPI documents additively, so B's policy should exist before A lands its first additive change (write the policy text first, the frozen-snapshot test after). C and D unblock E's demonstration (a UI on its own origin, a list to watch). Any item can be dropped without affecting the others.

## Non-goals
Authentication/authorization (the feed and the list assume the same trust as the rest of the API for now); a generic query language; GraphQL; replaying missed feed messages; a backend-for-frontend layer (reconsider only if the UI needs aggregation, offline mode or optimistic updates); changing any existing route, status or response body.

## Verification (every item)
`bun run typecheck`; `bun run test:unit`; the integration suites for the packages touched, **in batches of a few files** (all at once starts dozens of containers and hangs); `git status docs/api` shows only the intended, additive changes (A, D); `vite build` of the UI package; for E a manual two-tab pass in a real browser (none of the tooling in this environment could open one so far, so it is stated as a manual step).

## Size
About 7.25 days: A 0.75, F-guard 0.25, B 0.75, C 0.5, D 0.75, F (the split) 1.75, E 2, G spike 0.5 (adoption, if the spike says yes, is a separate plan).
