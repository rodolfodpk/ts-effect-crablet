# Plan: the API follow-ups the Foldkit page surfaced (seven items, ranked)

## Context
The Foldkit page (examples/course-enrolment-ui, tutorial step 5) was the first real client of the HTTP API, and the typed command client closed its biggest gap. What is left are product questions, each small enough to be its own piece of work. They come from two places: the findings recorded in NOTES.md ("Course UI") and the design discussion about one definition with two consumers (OpenAPI for any language, Foldkit for TypeScript + Effect). The recommendation from that discussion is the frame for everything below: **keep one definition and one transport; specialize only at the edges** (the contract/logic boundary, UI-only endpoint groups, and CORS; evolution rules for a public projection are deferred until an external consumer exists, ADR-0013).

## A. The server's 400 names the failing fields - DONE (phases 1-3; `InvalidInput.issues`, the `errors` member of the 400, `errors: "all"` so every field is reported; see NOTES "Field-level 400")
**Verified.** `defineCommand`'s `decodeInput` turns a `SchemaError` into `InvalidInput({ message })` (`packages/commands/src/Command.ts:158`), and `CommandApiLive` then discards even that and answers a fixed `Invalid payload for command: <name>` (`CommandApiBadRequest.of`). The derived TypeScript client validates the same Schema before sending and its `SchemaError` names the path (`at ["capacity"]`); every other client (curl, Python, the generated OpenAPI clients) gets nothing to act on. Checked by running it: a `SchemaError` exposes `.issue`, and `SchemaIssue.makeFormatterStandardSchemaV1()` turns it into `[{ path: ["capacity"], message: "Expected a value greater than or equal to 1" }]`. The built-in messages do **not** echo the received value (`Expected string`, `Expected number`, even for an input of `"secret-value"`).
**Decision.** The 400 problem gets an `errors` extension member (RFC 7807 allows them): `[{ path: ["capacity"], message: "..." }]`, built from the `SchemaError` issue. `InvalidInput` carries the structured `issues` next to `message`. `CommandApiBadRequest` gains an optional `errors` field, so the generated OpenAPI changes **additively** (policy B). The page shows the messages under the matching form field.
**Privacy.** The built-in messages carry no input value, so there is no leak to fix today. A custom message on a check could one day include one, and the repo has personal-data markers and redaction (Privacy P1-P3), so a test pins that a personal field's value never appears in a 400 body: a guard for future checks, not a response to a present problem.
**Phases.** (1) `InvalidInput.issues` + the extraction + unit tests, including the no-echo test; (2) the problem body, the OpenAPI document (regenerate; additive), the integration test (`errors[0].path` is `["capacity"]`); (3) docs and the page: no change is needed for the TypeScript page (its client rejects a bad payload before the request leaves, so the server's `errors` only matter to other clients); the page's `Rejected` case shows them when present, which costs a few lines; tutorial step 3/5 text says which side reports what; NOTES.
**Risks.** Path representation for nested/array inputs (use the formatter's path as is, document it); a future custom message leaking a value (the no-echo test); clients that parsed the old fixed `detail` (it stays unchanged); the request body that is not even valid JSON has no schema issues (it keeps the plain 400).

## B. Evolution rules for the OpenAPI projection - DEFERRED
**Decision (project owner).** The project is pre-release with no external consumers and makes no promise of API stability: a breaking change is fine whenever it is worth it. So the frozen-snapshot test, the diff tool and the versioned paths are **not built**. What exists is ADR-0013, which now says exactly that and keeps the additive/breaking vocabulary so a change is labelled honestly; the byte-for-byte comparison of `docs/api/*.json` stays as the drift alarm.
**Trigger to build it.** The first external consumer, or a declared 1.0. Then: freeze `docs/api/<name>-v1.json`, version by path prefix through the existing `basePath` (`/v1/commands`), and add a test that fails only on a BREAKING difference (spike first: an existing tool such as `oasdiff`, or a ~100-line structural diff over the parts we generate; measure it on real changes in this repo's history). Estimated 0.75 day.
**Effect on the other items.** None of them has to stay additive or carry a compatibility shim; each can choose the cleaner design.

## C. Optional CORS in `commands-http` - DONE (`corsLayer`, wired into the course app, the page's `VITE_API_URL`; see NOTES "Opt-in CORS")
**Verified.** The server has no CORS handling; the page uses a Vite proxy. Effect provides `HttpMiddleware.cors({ allowedOrigins, allowedMethods, allowedHeaders, exposedHeaders, maxAge, credentials })`. Gotcha in Effect's own docs: middleware passed to `HttpRouter.serve({ middleware })` wraps the whole server chain and **changes to the response are not reflected**; response-modifying middleware (CORS adds headers) must go through `HttpRouter.middleware`. The apps compose their own router (`HttpRouter.serve(makeCourseApiLayer(...))`), so the right shape is a helper the app opts into, not behaviour inside the group.
**Decision.** Export a `corsLayer(options)` (router-level middleware, deny-by-default: no option, no CORS headers) from `commands-http` with sensible defaults for this API (`exposedHeaders: ["X-Correlation-Id"]`, the methods and headers the routes use, `maxAge`), documented as "needed only when the UI is on another origin". The UI gets a `VITE_API_URL`-style base URL so it can run without the proxy; the proxy stays the default dev setup.
**Phases.** (0) Spike: `HttpRouter.middleware` + `HttpApiBuilder.layer` + the docs layer compose, and the preflight (`OPTIONS`) reaches the middleware; (1) the helper + docs; (2) integration test: an allowed origin gets `Access-Control-Allow-Origin` and the preflight succeeds, a disallowed origin gets no CORS headers, `credentials: true` with a wildcard origin is rejected at construction; (3) the page runs against the server on another port without the proxy.
**Risks.** A wildcard with credentials (rejected by construction); CORS middleware ordering against error responses (the test covers a 4xx and a 5xx from the API).

## D. A list/search read pattern - DONE (`GET /api/courses`, the page's list; see NOTES "Course list")
**Verified.** Both apps write their read endpoints by hand (course: one, `getCourse`; wallet: three) as an `HttpApiGroup` plus a `...Live` implementation over the app's own view tables; there is no list or search endpoint, so the page asks for a course id. No generic query machinery exists, and one is not warranted by two apps.
**Decision.** No query engine. (1) Add `GET /api/courses` to the course app: a keyset-paginated list over `course_seats_view` (`?limit=` bounded, `?after=<courseId>` cursor, optional `?q=<prefix>`), response `{ items: [...], next: string | null }`; parameterized SQL, no offsets. (2) The page gets a course picker fed by it, refreshed after each write (read-your-writes applies to the list too). (3) Extract a small `Page(Item)` response Schema and cursor helpers into `@crablet/views` **only if** the wallet app needs a list as well; otherwise they stay in the course app and the pattern is documented, not abstracted.
**Phases.** (1) The endpoint, the SQL, the OpenAPI document (additive), integration tests (ordering, limit bounds, `after`, `q`, empty); (2) the picker in the page + Story/Scene tests + the end-to-end test; (3) tutorial text and, if (3) above triggers, the extraction.
**Risks.** Premature abstraction (the "only if the wallet needs it" rule); unbounded `limit` (clamped and tested); `q` as a `LIKE` pattern (escape `%`/`_`).

## E. Live updates: a view-change feed - DONE (phases 0-4; see NOTES "Live updates" and ADR-0014)
**Verified.** The only notification today is `pg_notify('crablet_events')` when events are appended, which wakes the pollers; **nothing signals that a view has applied events**, so a client cannot know when a read has become fresh except by `?waitFor` (a held request) or by polling. Effect 4.0.0 has `HttpApiSchema.StreamSse` and an `Sse` codec, and `HttpApiClient` types SSE endpoints; Foldkit turns a stream into Messages with a Subscription (`Subscription.make`, `persistent`). Progress is now a `(transaction_id, position)` cursor (ADR-0012), which is exactly what a client holding its write's marker needs to compare - **but the HTTP command response carries only `lastPosition`** (`CommandCreated`); `lastTransactionId` exists on the server (`ExecutionResult`) and is not sent, so a page cannot make that comparison today.
**Decision.** A **ping, not data**: the feed says "view V advanced to cursor C"; the client re-reads. No row data crosses the feed (nothing to authorize or leak beyond a view name and a cursor; auth is a later, separate concern).
- *Source.* After the poller commits a view's progress update (`updateCursor`), `pg_notify('crablet_view_progress', '<view>|<xid>|<position>')`, **outside** the projection transaction (so a ping never precedes visibility) and best-effort (at-most-once is fine: clients re-read on every ping and on reconnect). The notify belongs to the poller package that owns the progress table, and it is **opt-in per progress table** (views only): the same tracker serves automations and the outbox, which must not emit pings.
- *Transport.* One endpoint, `GET /api/views/changes?views=a,b` (SSE), in a separate group/package (`views-http`), not in `commands-http`; coalesces bursts, sends a heartbeat comment, closes on server shutdown. One multiplexed connection per page (browsers cap HTTP/1.1 connections per origin).
- *The write marker.* Add `lastTransactionId` (a string, like `lastPosition`) to `CommandCreated` (an additive field; ADR-0013). For a client that does not use it, any ping for the watched view simply triggers a re-read.
- *Client.* A Foldkit Subscription over the stream emits `ViewAdvanced { view, cursor }`; `update` re-reads the open course when the cursor reaches the page's own write marker (the same pair comparison `waitUntilProcessed` makes) or when any ping arrives for the watched view. `?waitFor` stays as the request-scoped way.
**Phases.** (0) Spike - DONE, see "Spike results (E)" below; (1) DONE 2026-10-02: the notify after `updateCursor` (opt-in for views) + a poller integration test (a ping per advance, none on a failed batch, none for an automation) and `lastTransactionId` in the command response (OpenAPI regenerated; additive); (2) DONE 2026-10-02: the feed group + a server integration test (subscribe, write, receive a ping whose cursor covers the write; heartbeat; clean close); (3) DONE 2026-10-02: the page: Subscription, Story tests for the Message, the two-tab demonstration; (4) DONE 2026-10-02: docs, NOTES, an ADR for the signal (why a ping, why after commit, at-most-once).
**Risks.** Proxies and compression buffering SSE (the spike); many views x many clients (one `LISTEN` shared per process, fan-out in memory); reconnect storms (client backoff via Foldkit; the server does not replay, the client re-reads); a notify lost on a crash (re-read on reconnect covers it).

### Spike results (E) - done 2026-10-02, in the scratch spike project (nothing committed)
Everything the design needs works with Effect 4.0.0 and Foldkit 0.165.0. Four things to carry into the phases.
- **An SSE endpoint is an ordinary `HttpApi` endpoint.** `HttpApiEndpoint.get("changes", "/api/views/changes", { query, success: HttpApiSchema.StreamSse({ data: Advanced }) })`, implemented by returning a `Stream` of the data values. The response is `content-type: text/event-stream`, chunked, with `data: {json}` frames, and events arrive one at a time as produced (300 ms apart in the test), not at the end. The `data` form has no comment/heartbeat frames; not needed in v1, because the client reconnects whenever a connection ends or an idle timeout closes it.
- **The Vite dev proxy streams it incrementally** (also with a browser-like `Accept-Encoding: gzip, deflate, br`). A production reverse proxy may buffer: document it (for nginx, `proxy_buffering off` or the `X-Accel-Buffering: no` response header). Not verified in a real browser: none of the browser tooling in this environment could open one.
- **The derived client consumes it, typed.** `const stream = yield* client.views.changes({ query })` is a `Stream` of the decoded `Advanced` values (`{ view, position }`), delivered incrementally; stopping the stream aborts the request. **Teardown works end to end:** when the client stops (the Effect client) or is killed (a raw client, the same as closing a tab), the server's stream finalizer runs promptly, both directly and through the Vite proxy, so a closed tab does not leak a server-side stream.
- **A Foldkit Subscription is the right shape.** `Subscription.make<Model, Message>()(entry => ({ viewFeed: entry({ views: Schema.Array(Schema.String) }, { modelToDependencies: model => ({ views: model.watching }), dependenciesToStream: ({ views }) => feed(views) }) }))`, registered through the application config's `subscriptions`; the runtime starts and stops the stream as the Model's dependencies change (an empty `watching` list means no connection). Run under Node, the stream produced `ViewAdvanced` Messages and, when the server closed the stream after 3 events, **reconnected on its own** (three connections in one run). With the server DOWN a fixed 200 ms pause gave 11 `FeedLost` Messages in 2 s: the real feed needs an exponential backoff with a cap, reset on success. Tests: the entry's two functions are plain functions (testable under Node against a real server, as above), and `Scene.Subscription.emit(message)` feeds a Message to a scene as if the subscription produced it.
- **Shutdown is bounded by `gracefulShutdownTimeout`, not by the stream.** Closing the server's scope with one open stream does NOT hang for ever, but it waits for the stream until the Node server layer's graceful-shutdown timeout, **20 s by default** (measured: the stream was interrupted at 20.3 s). A "closing" signal completed from the feed layer's finalizer cannot help: layer finalizers run AFTER the server's drain. So servers that serve feeds set `NodeHttpServer.layer(..., { gracefulShutdownTimeout: "1 second" })` (with it, a close took under a second), and the test support does the same so `app.stop()` is fast. A maximum lifetime per connection (for example 5 minutes, after which the stream ends and the client reconnects) is a cheap extra for load balancers.
- Still to design in phase 2 (not spiked): one multiplexed connection per page (`?views=a,b`; browsers cap HTTP/1.1 connections per origin at about 6), coalescing bursts of pings, and where the course app mounts the feed group.

## F. Contract vs logic - DONE (phases 0-3; see NOTES "Contracts")
**Measured (corrects an earlier claim).** `bun build` of the page with a metafile: of 398 kB (minified), `effect` is 206 kB and Foldkit 158 kB; the course domain, the command pipeline and the event-store error types that the API definition drags in are **about 15 kB (under 4%)**. The split is therefore **not** about bundle size. It is about exposure:
- **Not an authorization hole.** The server stays the authority: the browser only sends HTTP, and `decide` runs in the server's executor against the real store; a copy of the code gives a client no power.
- **An exposure and hygiene problem.** `CourseApi.ts` imports the domain, so `decide`, the models and the event definitions (business rules, thresholds, event names, the tags that draw the consistency boundaries, `idempotentBy` queries) ship to the browser by default. A domain module that one day imports something server-only (config, a database client, Node's `crypto`) would break or poison the browser build or leak into it. "Shipped unless someone remembers to stop it" is the wrong default, and the migration gets bigger with every command and example added. So it is scheduled, not left to a trigger.
- **CI gap.** CI runs typecheck (including the UI's), unit tests and integration tests, but never builds the UI.

**Design.** A command splits into two parts that are already separable:
- the **contract** - `name`, `input` Schema, `errors` (and with them the domain error classes): public, browser-safe, already published by the OpenAPI document;
- the **behavior** - `model`, `decide`, `prepare`, `idempotentBy`, `retries`, `consistency`, ...: server-only.

`defineCommand` does not change. `commandContract({ name, input, errors })` returns a typed plain object that preserves the literal types (the `const` input Schema type and the `errors` tuple), and the server spreads it: `defineCommand({ ...SubscribeContract, model, decide })`, which yields the same `Command<In, Err, I, Es>` as today.
- *Files.* `domain/enrolment.contract.ts` (no server imports; the error classes live here) and `domain/Enrolment.ts` (events, models, behavior; imports the contract). A command that is never exposed (like `SendWelcomeNotification`) needs no contract and stays single-file.
- *The API definition* (`CourseApi.ts`) registers **contracts** (`exposedContract(SubscribeContract)`); `makeCommandApiGroup` takes contracts only. `exposedCommandOf(command)` is **removed**, not kept alongside: a breaking change is acceptable (ADR-0013), and two ways to register a command would let a server-only command object reach the browser path again. The typed client is unchanged (same `I` and `Es`).
- *The server* (`CourseApp.ts`) passes **implementations** to `makeCommandApiGroupLive`; a type (`Implements<typeof contracts>`) ties the two registries together, so a contract with no implementation, or a mismatched name, is a compile error: every route has code behind it.
- *The OpenAPI document* depends only on contracts, so it could be produced without loading any behavior.

**Effect on writing code.** Server: an exposed command is declared in two places (contract, then behavior); scenario tests, the executor and automations are untouched; events and models do not move. UI: no change to the code written (it already imports `course-enrolment-app/CourseApi` and uses the typed client); the bundle simply stops carrying `decide`, the models and the events. Costs: one more concept in tutorial step 3 ("the contract is the public part"), a naming/placement convention, and edits to the two examples, `exposed-command.test.ts` and the tutorial's `expose` block.

**Phases.**
- *Guard - DONE (ships with A).* A unit test that bundles `CourseApi.ts` for the browser (`Bun.build`/`bun build --target browser` with a metafile) and fails if the build fails or the output references `node:` modules or `pg`; with a negative control. Runs in CI through `test:unit`. After the split it is tightened (below). Built as `examples/course-enrolment-app/test/browser-safe.test.ts`: it bundles `CourseApi.ts` with `Bun.build` (target browser, metafile) in about 80 ms and fails on any Node module, `sql-pg`/`pg`, `platform-node` or server package (`event-poller`, `views`, `outbox`, `automations`, `db-migrations`, `test-support`); the negative control is the server entry `CourseApp.ts`, which must fail the same check, and a real mutation (a `node:os` import added to the domain module) was checked to make it fail.
- *0. Spike - DONE (see "Spike results (F)" below).* (a) `commandContract` preserves the `errors` tuple and the input Schema type, and `defineCommand({ ...Contract, ... })` is `Equal` to today's `Command` type (a type test); (b) `makeCommandApiGroup` over contracts gives the same typed client and a byte-identical OpenAPI document; (c) `makeCommandApiGroupLive` + `Implements<C>` give the compile error for a missing or mismatched implementation; (d) the metafile of a contract-only `CourseApi.ts` contains none of `Enrolment.ts`, `decide`, models or events, and by how much the bundle shrinks; (e) the guard runs in-process under `bun test` fast enough.
- *1. Core (0.4 day) - DONE, additively.* `commandContract`, `exposedContract`, the group/Live signatures, `Implements`, type tests (with controls); `exposedCommandOf` is removed and both examples are converted in the same change.
- *2. The course app (0.5 day) - DONE.* Split `Enrolment.ts`; `CourseApi.ts` registers contracts, `CourseApp.ts` implementations; the guard is tightened to fail if the browser bundle contains anything from the server-side domain module; OpenAPI documents unchanged; the UI package unchanged and its tests green; the tutorial's `expose` block and step 3 text follow.
- *3. The wallet app and docs (0.4 day) - DONE.* Same split for the five exposed commands; README, an addendum to ADR-0010/0011, NOTES.
**Risks.** `const` generics lose the tuple through the spread (spike (a)); two registries drifting (the `Implements` type); a contract file quietly importing a server module (the tightened guard); more ceremony for small apps (single-file `defineCommand` remains for commands that are not exposed over HTTP).

### Spike results (F) - done 2026-10-02, in a scratch worktree (removed; nothing committed)
The design holds; one shape improvement and one limitation to carry into phase 1.
- **(a) The contract keeps its types, and the spread is exactly today's command.** `commandContract({ name, input, errors })` keeps the literal name, the input Schema type and the error tuple (`readonly [A, B]`, and `readonly []` when none). `defineCommand({ ...Contract, model, decide })` has a type `Equal` to the one from the direct declaration, and the "every error `decide` can fail with must be declared" check still works for a contract held in a `const` (empty or partial: both produce the usual `undeclaredDomainErrors` error). **Foot-gun found:** writing the contract call INLINE inside the spread (`defineCommand({ ...commandContract({...}), ... })`) silently loosens the inferred error list, so the check stops firing. In real use the contract is an exported const in its own file, so it cannot happen by accident, but phase 1 pins it with a type test and the helper's comment says "always declare the contract as its own const".
- **(b) Same typed client, byte-identical OpenAPI.** A group built from contracts (`makeContractApiGroup(basePath, contracts, options)`) gives the same per-command typed client (payload checked, declared errors exact, `HttpClientError`/`SchemaError` in the channel); the UI package typechecks with NO change; regenerating both OpenAPI documents leaves `git status docs/api` empty. **Shape improvement:** contracts are passed as a LIST (`[DefineCourseContract, SubscribeContract]`) and the route name is the contract's own `name`, so the registry's key/name duplication (a key that could disagree with the command's name, unchecked today) disappears.
- **(c) `Implementations<typeof contracts>` ties the server to the contracts.** `const impls: Implementations<typeof courseContracts> = { define_course: DefineCourse, subscribe: Subscribe }` fails to compile for a missing implementation, an extra one, and a command built from a different contract (different errors or an unrelated input). **Limitation:** a command whose input Schema is strictly WIDER than the contract's (an extra field) is structurally assignable and is NOT caught by the type. The natural path (spreading the contract) cannot diverge, so the plan adds a cheap RUNTIME check at startup instead: when the server registers its implementations it asserts each command's `input` and `errors` are the very same objects as the contract's (reference equality), with a test.
- **(d) What the browser bundle stops carrying.** Course app split into `domain/enrolment.contract.ts` (errors + contracts, 409 bytes in the bundle) and `domain/Enrolment.ts` (events, models, behavior). Bundle of the page: 398 kB -> 377 kB (-21 kB, -5%); `Enrolment.ts` is absent; the command pipeline from `@crablet/commands` goes from 5.5 kB to 285 bytes. `CourseQueryApi.ts` had to import its error from the contract file too (it is part of the API definition).
- **(e) The guard tightens cleanly and means something.** Adding `domain/Enrolment.ts` and the pipeline modules (`Command`, `CommandExecutor`, `CommandDecision`, `Model`, `Event`, `Crablet`) to the forbidden list: the guard passes after the split and FAILS on today's code (it lists `Enrolment.ts` among the reached modules). Runs in about 90 ms.
- **What changes in the tutorial:** only the `expose` block (contracts instead of exposed commands) and the `subscribe` region (the spread); steps 1-2 keep single-file `defineCommand`.

## G. Foldkit server rendering (SSR/SSG) - an optional spike
**Verified.** Foldkit renders the same program on the server and hydrates it in place: static generation at build time or per-request rendering, under `foldkit/experimental/server` (the word "experimental" is Foldkit's own; Foldkit itself is beta). Its SSR example runs on an Effect HttpServer, which is what the course app already is, and initial data travels as serialized "flags" embedded in the HTML. Our own evidence: the integration test already imports the page's `main.ts` and runs its real Commands under plain Node with no DOM, so the program is server-safe in the sense that matters first (no DOM at import, Commands runnable). Not tried: rendering `view` to HTML and hydrating it.
**What it would and would not buy.** It would give a first paint that already contains data (a course catalog), indexable/link-previewable public pages, no loading flash, a page and an API from one deployable, and a literally isomorphic program (the same `update` and `view` on both sides, the same typed client fetching the data). The current page is an interactive tool with no SEO need, so it gains almost nothing today, and there is nothing worth rendering until the list endpoint (D) exists.
**Costs and risks.** An experimental API on a beta framework; hydration mismatches (the Model rendered on the server must equal the client's starting Model); how the server fetches its data (the typed client over HTTP, or the view queries in process) - either reads the lagging views, so a render can be slightly stale; hydration is not covered by Scene tests, so it needs its own test; more surface in the course app (a render route, a server entry); auth/cookies are a later concern. No conflict with F: the renderer is server code and may import the behavior; the browser bundle stays contract-only.
**Decision.** Spike first, commit later. No adoption work is scheduled.
**Spike (0.5 day, after D and F).** Answer four questions in a scratch worktree and record them here: (1) does Foldkit's SSR pattern work with our Model and Commands - init data via flags, or the init Commands resolved on the server - and what does `init` look like for each; (2) can the course app serve the page from its existing router (`/` and `/courses` next to the API, one process) without disturbing the API routes or the OpenAPI document; (3) does hydration keep the Model and the page's Subscription (E's feed, if it exists by then) working after the first paint; (4) does a server-rendered catalog page (from D's list endpoint) come out with the data in the HTML, and what is the cost of the extra server dependency in the bundle. Outcome: either a follow-up plan with phases (a render route, a hydration test, tutorial step 6) or a note here that it is not worth it yet.

## Order and dependencies
`A + F-guard` (done) -> `C` -> `D` -> `F (the split)` -> `E`; `G` (spike) after D and F, any time.
